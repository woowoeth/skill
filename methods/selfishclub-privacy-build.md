# privacy-build — 법정 문서 3종 초안 만들기

문서가 **아예 없는 상태**에서 시작해 개인정보 처리방침 · 마케팅 수신동의 · 이용약관의 초안을 만들고, 사이트에 실제로 붙일 코드까지 내놓는다.

**privacy-check와의 관계**
| | privacy-check | privacy-build (이 스킬) |
|---|---|---|
| 전제 | 문서가 이미 있다 | 문서가 없다 |
| 하는 일 | 실제 코드와 대조해 감사 | 초안 생성 + 구현 코드 |
| 결과 | 점검 리포트 | 문서 3종 + 붙일 코드 |

이 스킬로 만든 뒤 privacy-check으로 점검하면 한 바퀴가 돈다.

---

## 절대 규칙

1. **첫 응답에서 반드시 면책을 밝힌다.** 아래 0단계 문구를 그대로 쓴다.
2. **모르는 사실을 채우지 않는다.** 사업자등록번호, 대표자명, 주소, 위탁업체명처럼 사용자만 아는 값은 `[[여기를 채우세요: 사업자등록번호]]` 형태로 남긴다. 그럴듯한 가짜 값을 넣지 않는다.
3. **실제로 하지 않는 것을 문서에 쓰지 않는다.** 템플릿에 있다는 이유로 CCTV, 위탁사, 만 14세 미만 절차를 남겨 두면 그 자체가 위반 소지다. 확인되지 않은 블록은 지우거나 사용자에게 묻는다.
4. **조문의 항 번호를 본문에 박지 않는다.** 2026년 9월 11일 시행 개정법으로 개인정보 보호법 제34조의 항 배열이 바뀐다. 문서에는 `개인정보 보호법 제34조에 따라`처럼 **조까지만** 쓴다.
5. **법률 자문이 아니다.** 유료 서비스, 만 14세 미만, 의료·금융 정보, 해외 이용자(GDPR/CCPA)가 걸리면 그 지점을 명시하고 전문가 검토를 권한다.

---

## 0단계 — 면책과 범위 안내

먼저 이 블록을 그대로 출력한다.

> **시작 전에 알려드립니다**
>
> 이 스킬은 **초안 생성 도구**이고 법률 자문이 아닙니다. 만들어 드리는 문서는 그대로 쓰는 완성본이 아니라, 빈칸을 채우고 사실을 대조한 뒤에 쓰는 출발점입니다.
>
> - 기준: 대한민국 법 (개인정보 보호법 · 정보통신망법 · 전자상거래법 · 약관규제법)
> - 다루지 않는 것: 만 14세 미만 아동, 의료·금융 정보, 해외 이용자(GDPR·CCPA), 오프라인 사업
> - 유료 결제가 있는 서비스는 초안까지만 만들고 **전문가 검토를 반드시 받으세요**
>
> 진행할까요?

## 1단계 — 서비스를 먼저 본다

문서를 쓰기 전에 **이 서비스가 실제로 무엇을 수집하는지** 확인한다. 순서를 바꾸면 안 된다. 실제와 다른 문서가 나오면 없느니만 못하다.

입력을 하나 고르게 한다.

| 입력 | 할 일 |
|---|---|
| **코드 저장소** | 아래 스캔 체크리스트를 실행 |
| **배포된 URL** | 폼 필드, 푸터 링크, 쿠키/트래커를 확인 |
| **말로 설명** | 2단계 인터뷰만으로 진행 |

### 코드 스캔 체크리스트

찾아야 하는 것 — 발견한 것만 적고, 없으면 "없음"으로 남긴다.

```
□ 폼 입력 필드          → <input>, <form>, react-hook-form, zod 스키마
□ DB 테이블 컬럼        → schema.sql, migrations/, prisma/schema.prisma, supabase 타입 정의
□ 서드파티 SDK          → GA, GTM, Amplitude, Mixpanel, Hotjar, Sentry, Channel Talk, 픽셀
□ 쿠키 / 로컬스토리지    → document.cookie, localStorage, 세션 라이브러리
□ 외부 API로 나가는 데이터 → OpenAI, Anthropic, Resend, SendGrid, Solapi, 카카오, Stripe, 토스
□ 호스팅 · DB 리전       → Vercel, Netlify, Supabase, Firebase, AWS 리전 설정
□ 파일 업로드           → Storage 버킷, 이미지 업로드
□ 로그인 방식           → 이메일/비번, OAuth(구글·카카오·깃허브), 매직링크
```

### 결과를 표로 정리해서 보여준다

| 수집 항목 | 어디서 | 왜 (목적) | 어디에 저장 | 누구에게 나가나 |
|---|---|---|---|---|
| 이메일 | 신청 폼 | 신청 접수·안내 발송 | Supabase `signups` | Resend (발송) |
| 접속 로그 | 자동 | 서비스 운영 | Vercel | — |

**이 표가 문서 3종 전체의 뼈대다.** 사용자에게 "빠진 게 있나요?"를 반드시 묻고 확정한 뒤 다음으로 간다.

## 2단계 — 인터뷰 (분기)

한 번에 하나씩 묻는다. 코드에서 이미 확정된 건 다시 묻지 않는다.

### Q1. 서비스가 지금 어디까지 하나요?

| 답 | 문서 두께 |
|---|---|
| **A. 이메일·연락처만 받는다** (결제 없음, 회원가입 없음, 신청 폼만) | 처리방침 얇게 · 수신동의 필수 · 이용약관 **선택** |
| **B. 회원가입·로그인이 있다** (결제 없음) | 처리방침 + 파기·보유기간 · 이용약관 **필요** |
| **C. 결제가 있다** | 위 전부 + 전자상거래법 표시사항 + 청약철회 · **전문가 검토 필수** |

### Q2. 사업자등록이 있나요?

| 답 | 처리 |
|---|---|
| **있다 (개인사업자 / 법인)** | 상호·대표자·주소·사업자등록번호를 문서에 표시 |
| **없다 (개인 명의)** | **아래 「사업자가 없는 경우」 분기로** |

#### 사업자가 없는 경우

사업자등록이 없어도 **개인정보 처리방침 의무는 그대로 있다.** 개인정보 보호법은 "개인정보처리자"를 대상으로 하고, 사업자 여부나 유·무료를 따지지 않는다.

| 항목 | 사업자가 없을 때 |
|---|---|
| 상호 | 서비스명으로 대체 (예: "○○ (개인 운영 서비스)") |
| 대표자 / 개인정보 보호책임자 | **본인 실명** — 닉네임은 피한다 |
| 주소 | 집 주소를 쓰기 어렵다면 **연락 가능한 이메일 하나로 갈음**하고, 주소는 빈칸 표시 |
| 사업자등록번호 | 표기하지 않음 |
| 통신판매업 신고번호 | 해당 없음 (무상이면 통신판매 자체가 없음) |
| 이용약관 | 전자상거래법 표시 의무는 사정권 밖일 수 있으나, **서비스 중단·계정 정지·책임 제한의 근거로 여전히 필요** |

**반드시 함께 말해줄 것** — 유료 전환하는 순간 사업자등록과 통신판매업 신고 검토가 필요해진다. 그때 문서를 다시 손봐야 한다.

### Q3. 마케팅 메시지를 보낼 건가요? 어떤 채널로?

채널을 **복수 선택**으로 받는다. 이메일 / SMS·LMS / 카카오 알림톡 / 카카오 친구톡 / 앱 푸시 / 안 보냄.

⚠️ **매체를 반드시 열거해서 동의를 받아야 한다.** "SMS 수신동의"만 받아 두고 카카오톡으로 광고를 보내면 위법 소지가 있다 (KISA 7차 안내서 기준, 문자와 메신저는 별개 매체).

### Q4. 서비스를 어디에 올렸나요? (국외 이전)

Vercel · Netlify · Supabase · Firebase · AWS 해외 리전 · OpenAI/Anthropic API · Resend · Stripe 중 하나라도 쓰면 **개인정보가 국외로 나간다.** 처리방침에 국외 이전 항목을 반드시 넣는다.

**바이브 코딩 스택에서 가장 흔한 누락이다.** 코드에서 확인되면 묻지 말고 바로 넣는다.

### Q5. 자동 수집 도구를 붙였나요?

GA · GTM · Amplitude · Hotjar · 채널톡 · 픽셀 → 쿠키/자동수집 항목 필요.

## 3단계 — 문서 3종 초안 생성

`references/` 를 읽고 만든다. **필요한 것만 읽는다.**

| 만들 문서 | 읽을 파일 |
|---|---|
| 개인정보 처리방침 | `references/02_privacy-policy.md` |
| 마케팅 수신동의 | `references/03_marketing-consent.md` |
| 이용약관 | `references/04_terms.md` |
| 조문·과태료를 인용해야 할 때 | `references/01_legal-basis.md` |

파일로 저장한다.

```
개인정보처리방침.md
마케팅수신동의.md
이용약관.md
```

**각 문서 맨 아래에 반드시 붙인다:**

```markdown
---
- 공고일 / 시행일: [[YYYY년 MM월 DD일]]
- 이 문서는 초안입니다. 빈칸([[ ]])을 채우고, 실제 서비스와 대조한 뒤 게시하세요.
```

## 4단계 — 사이트에 붙일 코드

`references/05_implementation.md` 를 읽고 만든다. 사용자의 스택(Next.js / React / 순수 HTML)에 맞춰 낸다.

내야 하는 것:

1. **동의 UI** — 필수/선택을 분리한 체크박스. 일괄 동의 금지
2. **`/privacy` · `/terms` 페이지** — 마크다운을 렌더링하거나 정적 페이지로
3. **푸터 링크** — 처리방침은 **홈페이지에 지속적으로 게재**해야 한다
4. **DB 스키마** — 동의 기록 컬럼. 아래는 나중에 못 고치는 부분이므로 반드시 포함한다

```sql
marketing_consent          boolean   default false,
marketing_consent_at       timestamptz,          -- 2년 재확인 의무의 기준점
marketing_consent_channels text[],               -- ['email','sms','kakao'] 매체별 동의
marketing_consent_version  text,                 -- 동의받은 문서 버전
terms_agreed_at            timestamptz,
privacy_agreed_at          timestamptz
```

> **`marketing_consent`를 boolean 하나로만 저장하면 2년차에 대응이 불가능해진다.** 정보통신망법상 동의일로부터 2년마다 수신동의 여부를 확인해야 하고, 확인할 때 "동의한 날짜"를 고지해야 한다. 스키마 단계에서 결정되는 문제라 나중에 고치기가 가장 어렵다.

## 5단계 — 마무리 점검표와 남은 숙제

### 붙이기 전 체크

```
□ 문서 안의 [[빈칸]]을 전부 채웠다
□ 처리방침의 "수집 항목"이 1단계 표와 정확히 일치한다
□ 실제로 하지 않는 항목(CCTV·위탁·만14세미만 등)을 지웠다
□ 개인정보 보호책임자 이름과 연락처를 적었다  ← 소상공인도 기재 의무는 있음
□ 국외 이전(Vercel·Supabase·OpenAI 등)을 적었다
□ 푸터에 처리방침·이용약관 링크가 있다
□ 동의 체크박스가 항목별로 분리되어 있다 (이용약관 / 개인정보 / 마케팅)
□ 마케팅 동의 문구에 매체를 열거했다
□ 동의 일자를 DB에 저장한다
```

### 이 스킬로 해결되지 않는 것 — 반드시 말해줄 것

- **유료 결제** → 전자상거래법 표시사항, 통신판매업 신고, 청약철회 조항. 전문가 검토 필요
- **만 14세 미만** → 법정대리인 동의 절차가 따로 필요
- **해외 이용자** → GDPR·CCPA는 이 스킬 범위 밖
- **2년마다 수신동의 재확인** → 문서가 아니라 **운영 절차**. 캘린더에 넣거나 자동화 필요
- **개인정보 유출 시 신고** → 개인정보 보호법 제34조. 2026년 9월 11일 시행 개정법에서 유출 "가능성"까지 통지 대상이 되고 항 배열이 바뀐다

마지막으로 **다음 단계**를 안내한다.

> 초안이 나왔으면 `privacy-check`로 한 번 돌려보세요. 문서와 실제 코드가 어긋난 곳을 잡아 줍니다.

## 톤

- 겁주지 않는다. "이만큼은 해두자" 수준으로.
- 법 조문을 앞세우지 않는다. **무엇을 해야 하는지 먼저**, 근거는 뒤에.
- 모르면 모른다고 한다. 빈칸을 남기는 게 지어내는 것보다 낫다.
- 한 번에 질문 하나.
