# GitHubで作業を完了する

変更・成果物作成の依頼を、GitとGitHubで計画からスカッシュマージと作業環境の整理まで進める。
相談・比較・説明・読み取りのみの調査には、この作業サイクルを要求しない。
調査から変更・成果物作成に進む場合は、その着手前に本スキルを適用する。

## 計画から実行まで

ユーザーが実施内容と検証方法を確認してから変更を開始できるよう、文書のみ・小さな修正も次の順序で進める。関連の薄い追加依頼の記録だけは例外とし、[後続Issueの記録手順](references/planning.md#関連の薄い追加依頼の記録)に従う。

1. 読み取り調査で目的・成果物・対象ファイル・変更内容・検証・完了条件を具体化する。
2. 計画をIssue本文に保存する。既存Issueも今回実行する計画として確認・更新する。
3. 保存したIssueを再取得して本文一致を確認し、[Issue保存後のブラウザ起動](references/planning.md#issue保存後のブラウザ起動)に従って既定ブラウザで一度開く。表示を確認し、URLと本文をユーザーに提示する。
4. ユーザーが `/goal #<Issue番号>` のようにIssueを指定してゴールを開始した場合（引用しただけの説明・相談を除く）は、そのIssueの実装開始を承認したものとして扱い、承認を再質問しない。それ以外は「この計画で実行・実装を開始してよいですか？」と質問し、明示的な承認を待つ。
5. 承認後に作業ブランチを準備し、編集・検証・コミット・PR・レビュー・マージへ進む。

> [!IMPORTANT]
> 承認前は読み取り調査、計画の作成・調整、Issueへの記録と提示まで。コード・文書・評価データ・生成物の編集、ブランチ作成・切り替え、コミットなど実装を進める操作は行わない。Issueを指定したゴール開始指示を除き、最初の依頼、Issueの存在、無回答は計画承認ではない。

承認済み範囲では各操作を再確認しない。範囲追加・方針変更はIssue更新、変更後の本文提示、再承認を経て実行する。詳細は [計画と作業ブランチの準備](references/planning.md) に従う。

## 段階ごとに読む資料

1. 変更への着手前と作業中の追加依頼を受けたときに[計画と作業ブランチの準備](references/planning.md)を読む。
2. コミット前に[コミットメッセージ](references/conventional-commits.md)を読む。
3. PR作成・レビュー対応・リベース・マージ・作業環境の整理の前に[レビューとマージ](references/review-and-merge.md)を読む。

コード変更では `bdd-tdd`、文書の作成・更新では `okf-docs` も適用する。
資料に書かれたプロジェクトのパスは作業対象リポジトリを基準とし、資料へのMarkdownリンクは本スキルを基準に解決する。

新規Issue（Sub-issue・計画なしの後続Issueを含む）と計画の保存・更新では、上記の共通起動手順を適用する。起動の都度確認は求めず、起動失敗時は保存成功と区別して理由・URLを伝え、承認済み作業を継続する。

## Markdownの投稿・更新

- Issue・PR本文・コメントの新規投稿と更新前に[GitHub向けMarkdownの品質](references/markdown-quality.md)を読み、GFMで構成し、共通rumdl設定で本文全体を整形・チェックする。
- 投稿後に本文を再取得し、保存内容とGitHubでのレンダリングを確認する。追記時も同じ手順を省略しない。
- rumdl未導入・旧版の場合の導入やダウンロードは、同資料に従って事前にユーザーの許可を得る。

## GitHubでの参照表記

- Issue・PRの本文とコメントでは、Issue・PR番号やコミットSHAを日本語や句読点に続ける場合、前後に半角スペースを入れ、コード記法で囲まない。GitHubで自動リンクされることを投稿後に確認する。

## コミットとプッシュ

- コミットメッセージは[コミットメッセージの指示](references/conventional-commits.md)に従う。
- テスト追加、テストを通す変更、リファクタリングなど、検証可能な小さな単位でコミットする。
- TDDではレッド・グリーン・リファクタリングの1サイクルを完了したらリモートへプッシュする。
- 文書変更などTDDを適用しない作業では、変更を検証・コミットしたらリモートへプッシュする。

## 実行と障害対応

- 計画承認後は承認済み範囲の成果物の作成と検証まで進め、提案や計画だけで終えない。
- 変更前に既存の差分を確認し、依頼と関係のない変更を上書き・取り消ししない。
- 依頼の達成に必要な範囲を変更し、無関係な改善は別の提案として扱う。
- 長い作業では、判明したこと、残る課題、次に行うことを区切りごとに共有する。
- 追加依頼は[計画手順の関連性判断](references/planning.md#関連の薄い追加依頼の記録)に従う。関連の薄い依頼は、計画作成・承認フローの例外として計画なしの独立した後続Issueへ記録し、現在のタスクを承認済み範囲で継続する。関連する範囲追加は計画更新・再承認を行い、不明なら確認する。
- 失敗した場合は原因を調べ、根拠のある修正や代替手段を試す。同じ操作を理由なく繰り返さない。
- ユーザーの判断や追加の権限が必要になった場合は、必要な理由と対象の操作を具体的に伝える。
- 障害で進められない場合は、完了した範囲、未完了の範囲、再開に必要な情報や対応を報告する。

## 検証と完了

- 成果物に対応する検証を、計画で定めた方法で実行する。
- 文書のみの変更では、記述の整合性、記載したパスやコマンド、差分の体裁を確認する。
- 最終的な成果物と差分を確認し、依頼との一致、変更漏れ、既存機能への影響を点検する。
- 完了条件を満たし、対応する検証に合格し、PRのスカッシュマージと「レビューとマージ」に定める作業環境の整理を確認して完了を報告する。
- 最終報告には対象のIssueまたはSub-issue、PR、成果、実行した検証とレビューの結果、マージ状態、mainの更新とブランチ削除の結果、残る課題を含める。
- 検証を実行できなかった場合は、その理由と未確認の範囲を伝え、検証済みとして扱わない。
