# Code City

You produce **one HTML file**: an isometric city of a repository. Buildings are modules.
Height is a metric you measured. Roads are call sites you found. A side panel explains each
module, and every claim renders next to the quoted source it came from.

You do **not** write the renderer. `city-template.html` sits beside this file and contains
all of it — projection, camera, hit-testing, theming, the index rail, the panel, the trace
player. You copy it byte-for-byte and replace exactly one object.

> **The one thing that makes this worth doing:** the picture is the delivery vehicle; the
> *findings* are the product. A faithful, beautiful restatement of the file tree is a toy —
> the reader already has a file tree. What earns a share is telling someone something about
> their own repo they did not know, with a click through to the line that proves it.

---

## Three rules that override everything below

**1. Falsifiable or deleted.** Every non-obvious claim carries a verbatim quote of the source
it came from, rendered beside it. A `file:line` proves a line exists; it proves nothing about
the sentence attached to it. If you cannot paste the ≤12 lines that support a claim, the claim
does not ship.

**2. No quotas.** Every count in this document is a ceiling, never a target. Zero sharp edges
for a module is a correct and expected answer. If every module has the same number of anything,
you generated it rather than found it.

**3. Prose may point, never supply.** A README, a doc comment, or a commit message may tell you
*which* path to go verify. It may never be the evidence for a hop, an edge, or a quirk. If the
docs describe a flow you cannot ground in code, it goes in `unknowns`, not in `flows`.

---

## Step 1 — Census. Never `wc -l` the tree.

A naive count is wrong by two orders of magnitude. Measured on one real repo: `6,605,994` lines,
of which the single largest "file" was a **1.4-million-line binary build cache**, against ~45,000
lines of actual source.

```bash
set -o pipefail
git rev-parse --git-dir >/dev/null 2>&1 && echo GIT || echo NOGIT
git ls-files | wc -l          # tracked
find . -type f | wc -l        # on disk — expect a 100x gap
```

Use `git ls-files`. It gives you `.gitignore` compliance for free and is the difference between
a fast survey and a hung agent. Without git, fall back to `find` with the exclusion list below.

**Exclude before counting, not after.** Literal list — do not "use judgement":

```
node_modules/ target/ dist/ build/ out/ .next/ .nuxt/ vendor/ third_party/
Pods/ .venv/ __pycache__/ coverage/ .turbo/ .cache/
*.min.* *.map *.lock *lock.json *.snap __snapshots__/ testdata/ fixtures/
*.svg *.png *.jpg *.jpeg *.gif *.mp4 *.woff* *.wasm *.pb.* *.ipynb_checkpoints
```

Also: treat any **nested `.git`** as a vendored subtree, and skip any single file over
20,000 lines after exclusion — list it under `unknowns` instead.

Count in **one pass**. A per-file loop is ~40x slower and times out on large repos:

```bash
git ls-files -z -- 'src/*' | xargs -0 wc -l 2>/dev/null \
 | awk '$2 != "total" { n=split($2,p,"/"); k=(n>2 ? p[1]"/"p[2] : $2); s[k]+=$1 }
        END { for (g in s) printf "%8d\t%s\n", s[g], g }' | sort -rn
```

> `xargs` splits past ARG_MAX, so `wc` emits **several** `total` lines. The `$2 != "total"`
> guard is load-bearing — without it your line counts roughly double on a big repo.

**macOS matters.** These are GNU-only and fail on BSD: `grep -P`, `find -printf`, `stat -c`,
`readlink -f`, `xargs -r`, `sed -i` without an argument. Use `grep -E` / `grep -oE`,
`wc -c < file`, and `find -not -path`.

## Step 2 — Classify every module before you measure it

Three buckets. This is not optional: on one real repo, **12 generated client directories**
would have won line count, won "public API surface" (a generated client is *nothing but*
public API), won fan-in, and shown zero tests — making the tallest, best-connected,
most-alarmingly-untested buildings code no human wrote or reads.

- **generated** — `@generated` / `DO NOT EDIT` / `Code generated by` in the first 5 lines of
  most files; a sibling schema (`*.proto`, `*.idl`, `*.graphql`, `openapi.*`); a path segment
  of `generated|__generated__|gen|pb`; or a codegen step in the build manifest.
- **vendored** — third-party source committed into the tree; a nested `.git`; a UI kit copied
  in wholesale rather than installed.
- **authored** — everything else.

Generated and vendored modules **still appear** (they are real, and things depend on them) but
carry `kind:'generated'` / `kind:'vendored'`, which excludes them from the rankings and labels
them in the panel. Never silently drop them — a reader who knows the directory exists and
cannot find it will distrust the whole page.

## Step 3 — Partition until you land in range

**You are aiming for 12–40 buildings.** That is the target, and reaching it is your job.
Do not take the first rule that fits and stop — decompose until the count lands in range.

Start from the largest natural unit and go deeper while the count is too low:

1. **Workspace members** — `go.work`, `Cargo.toml` members, `package.json` workspaces, `pnpm-workspace.yaml`.
2. **Package manifests** — every `package.json`, `pyproject.toml`, `go.mod`, `*.csproj`, `Gemfile`.
3. **Top-level directories** of each source root.
4. **Second-level directories** inside any module that is still too big.

**The recursion rule, and this is the one that matters:** after each pass, split any module
holding more than 15% of the repo's authored lines, and keep splitting until nothing does or you
hit 40. A single-package app is not one module — a repo with one `package.json` and
`src/{components,lib,hooks,pages}` is **four modules at least**, and probably more once you look
inside the big ones. Stopping at rule 2 with N=1 is the most common way to get this wrong.

Merge in the other direction too: a directory of three tiny files is not a building. Fold leaves
into their parent until each module is something a person would name in conversation.

| N after decomposing | What you do |
|---|---|
| **fewer than 25 authored source files in the whole repo** | Say so in two sentences and stop. There is nothing to draw. |
| **N < 12** | You did not go deep enough. Recurse into the largest modules and re-count. |
| **12–40** | Build it. This is the target. |
| **41–90** | Fold the smallest modules into their parents until you are under 40. |
| **> 90** | Districts become the buildings, or pick a subtree by a stated rule. Say what you left out. |

Legibility is the binding constraint. Measured: at 30 modules 18 labels are readable; at 120,
twenty; at 600, fifty-four. The renderer is fine at 600 — the reader is not.

**Then show the manifest and keep going.** Print one line per module — name, path, kind, files,
lines — so the user can see what you are about to describe. Do **not** wait for approval; carry
straight on into Step 4. Only stop if something is obviously wrong: a build directory survived,
the count is still out of range, or you cannot tell what the repo does at all.

**Every module in that manifest gets a building.** Coverage is not the thing you trim when the
repo is large — depth of prose is. A module you have little to say about gets two sentences and
still gets drawn. A city missing a third of the repo is a failed run, not a fast one.

## Step 4 — Measure

Per module: `loc` (authored lines), `files`, `tests`, `api`. **Do not author `fanin`** — the
template derives it from your edge list so it can never disagree with the wires on screen.

`api` means externally callable entry points: exported symbols, HTTP routes, `pub` items, RPC
methods. It is not comparable across languages — a TS file with no export discipline scores
"file count × 4" while Rust `pub` is deliberate. If the repo is polyglot, say so in `unknowns`.

**Never invent a number.** If you cannot measure something, set it to `0` and record why in
`unknowns`. A fabricated count produces a confidently wrong skyline, which is worse than a flat one.

## Step 5 — Wires

An edge is a real call site with a citation. Prefer few and verified over many and inferred:
four confirmed cross-boundary edges are worth more than four hundred intra-package imports.

```bash
# imports (cheap, and a good first pass)
git ls-files -z -- '*.ts' '*.tsx' '*.js' '*.py' '*.go' '*.rs' \
 | xargs -0 grep -noE "(from|require\(|^import|^use )[[:space:]]*['\"][^'\"]+['\"]" 2>/dev/null
```

Then chase the edges that cross a **language or process boundary** — those are the interesting
ones and the ones a naive import scan misses entirely.

Mark `kind:'read'` for a read-only call; it renders dashed.

## Step 6 — Traces

A trace is one path through the system. **Each hop declares how you know it**, and the template
renders that label:

- `k:'CALL'` — you cited both the call site and the definition.
- `k:'ENTRY'` — an HTTP route, CLI command, event handler, or `main`.
- `k:'GAP'` — the two sides never call each other. Name the shared medium (chain state, a queue
  topic, a DB table, a poll interval) and cite the **write site and the read site separately**.

The `GAP` type exists because the most important path in a real system often has *zero* import
edges. On one repo the central flow — place a bet, a bot notices resolution, propose, finalize,
claim — crossed two process boundaries through shared state and a 30-second poll. An import
tracer either misses it or reads the README and narrates it while implying it derived it. The
second is worse, because it is unfalsifiable.

A hop you cannot ground is a `GAP` or it is not a hop. Ceiling: 8 traces, 12 hops each.

## Step 7 — Prose

Three fields per module: `one` (≤12 words), `what`, `built`. Plus `quirks`.

**Banned openers.** Do not begin with the module name followed by *is responsible for*,
*handles*, *manages*, *provides*, or *serves as*. That sentence shape is the single clearest
signature of generated text.

**Every module's prose must contain at least one fact obtainable only by reading the code** —
a specific number, an identifier, an ordering constraint, a default value. Name files inline.

**Length must vary, a lot.** Modules differ in how interesting they are. A boring one gets two
sentences. An interesting one gets eight. Uniform paragraph length across modules is the
strongest possible tell that the analysis was generated rather than performed.

**Sharp edges** (`quirks`) are the most valuable and most fabricated part of the page. Restrict
them to claims that leave a textual fingerprint:

- a comment giving a reason or a warning (`TODO`, `HACK`, `XXX`, `because`, `careful`, `don't`)
- an error that is caught and swallowed or downgraded
- an unexplained magic constant
- a retry, timeout, sleep, or poll interval
- a fallback or compatibility branch
- an ordering or initialisation constraint the code enforces
- a guard that is conspicuously **absent** where its siblings have one

Each carries `q:` — the verbatim source span, ≤12 lines — which the page renders beneath the
claim. **No quote, no quirk.** A claim requiring you to infer intent from clean, unremarkable
code is not a sharp edge; it is a guess wearing a citation.

## Step 8 — Layout

Hand-place on an integer grid. `gx,gy` is a building's **north corner**, `w,d` its extent.
Screen depth is `gx+gy`: low is far and hazy, high is near the viewer.

Hard constraints — the painter's algorithm has no splitting, so violating the first one
produces visibly wrong overlaps:

- **No two building rectangles may overlap.** Same for district rectangles.
- Every building lies fully inside its district; every district inside `bounds`.
- Uniform `w×d` within a district (4–6 units), varying between districts. Footprint carries no
  data — equal footprints keep the height comparison honest. Never below 3×3.
- 1–2 unit alleys between buildings; 2–3 unit margins to the plate edge; **4–8 unit gutters
  between districts, reserved for wires**.
- Order districts along the `gx+gy` diagonal: upstream and foreign things far, the thing you
  want the reader to land on near.
- **Max 6 districts.** Only six hues are validated for colourblind separation in both themes;
  a seventh cannot be reliably distinguished. Merge instead.

**Wires** route through the gutters as `via:[[x,y],…]` in absolute grid coordinates. Offset
parallel wires in the same corridor by 0.6–0.8 units so they do not overprint. A wire stub may
pass under its own neighbours; a long haul must not cross an unrelated building. Both directions
of a mutual relationship need two edge records in different lanes.

## Step 9 — Take the repo's colours

A Rust CLI should not look like a React app. Before you emit, spend two minutes finding what
this repo actually looks like, and retint the city to match.

Where to look, in order — stop at the first that gives you a real accent:

```bash
git ls-files | grep -iE 'tailwind\.config|theme|tokens|design|palette|_variables|globals?\.css' | head
git ls-files -z -- '*.css' '*.scss' | xargs -0 grep -hoE '^\s*--[a-z-]*(primary|accent|brand|main)[a-z-]*:\s*#[0-9a-fA-F]{3,8}' 2>/dev/null | head
git ls-files -z -- '*.ts' '*.js' '*.json' | xargs -0 grep -hoE '"(primary|accent|brand)"\s*:\s*"#[0-9a-fA-F]{3,8}"' 2>/dev/null | head
```

Also worth a look: the README's badges, a logo SVG's fill colours, a `theme` block in
`docs/` config. If the repo has no design language at all — a CLI, a library, a set of
contracts — pick from what it *is* rather than inventing: warm greys and amber for a build
tool, deep blue for infrastructure, near-black and green for a terminal-shaped thing. Say in
the Limits tab which you did.

Then edit **only** the token block at the top of the template, the one marked
`▼▼▼ THE ONLY REGION YOU MAY RETUNE ▼▼▼`:

- `--accent` / `--accent-ink` — the repo's primary. This is the selection colour and the one
  people will read as "the brand".
- `--warm` — the trace colour. A second brand colour, or a complement.
- `--bg`, `--surface`, `--surface-2`, `--surface-3`, `--c-ground`, `--c-sky`, `--c-haze` — the
  ground the city sits on. Retint these together toward the repo's mood; they must stay a
  smooth ramp or the buildings stop reading as solid.
- `--ink`, `--ink-2`, `--ink-3`, `--ink-4` — text, on the same hue bias as the ground.

**Retune light and dark together.** There are three token blocks — bare `:root`, the
`prefers-color-scheme` block, and `[data-theme="dark"]`. Change one and you have broken the
other two.

**Leave `--d1..--d6` alone** unless you can genuinely re-derive six hues that keep their
separation for colourblind readers in both themes. They carry district identity and they are
validated; a prettier palette that fails that is a regression. Retinting the accent and the
ground is enough to make the city feel like the repo.

Check your work: `--accent` must clear 3:1 against `--bg` in both themes, and text tokens must
stay legible on their surface. If a colour you pulled from the repo fails that, keep the hue and
move the lightness until it passes.

## Step 10 — Emit two files

The data is the artefact; the page is one view of it. Write both.

**`repo-city.json`** — the `CITY` object as plain JSON. This is the source of truth. It is
diffable, so `git diff repo-city.json` between two runs shows what actually changed in the
architecture instead of 1,800 rewritten lines. It is also a far better context payload for the
next agent session than the raw repo.

**`repo-city.html`** — the template with that object inlined. Self-contained on purpose: it must
open from `file://`, offline, on someone else's laptop, with no server. Do not make the page
fetch the JSON — `file://` blocks it.

```bash
cp "$SKILL_DIR/city-template.html" ./repo-city.html
# then replace the `const CITY = {…};` object with the contents of repo-city.json
```

Replace **only** that object. Do not reformat, rename, refactor, or "improve" anything else in
that file. The design is authored — the shading ramps, the tile geometry, the easing constants,
the validated palette. Re-derived, it becomes default blue, flat lighting, and rounded corners:
exactly the generated look you are trying to avoid.

## Step 11 — Gates. Do not say "done" before these pass.

Then **open the file** and look at it. The gates check structure, not composition.

## Step 12 — Show it

Do not end by reporting that two files exist. Open the thing.

```bash
sh "$SKILL_DIR/../../scripts/serve.sh"          # opens repo-city.html
sh "$SKILL_DIR/../../scripts/serve.sh" --server # if you are in a container
```

If those scripts are not beside the skill, do it directly:

```bash
open repo-city.html || xdg-open repo-city.html || echo "open $(pwd)/repo-city.html"
```

Use `--server` when you are running in a container, over SSH, or anywhere without a
browser — it backgrounds a server on a free port and prints the URL and the PID to
stop it. It returns immediately; never run a blocking server in the foreground, it
will hang you.

Then say, in two or three sentences, the most interesting thing the survey turned up —
the module nothing depends on, the generated directory that outranked real code, the
gap between what the docs claim and what the tree holds. The page is the artefact; that
sentence is why anyone opens it.

## The data contract

```js
const CITY = {
  meta:   { repo:'name', sha:'abc1234', date:'YYYY-MM-DD', tool:'git ls-files + wc -l',
            excluded:'what you left out and why' },
  bounds: { x0:0, y0:0, x1:74, y1:64 },          // must enclose every district
  repo:   [{ v:'21', l:'modules' }, …],           // the top strip
  unknowns: ['what you could not determine', …],  // required, non-empty

  districts: [{ id, label, slot:1..6, x0, y0, x1, y1, blurb }],

  buildings: [{
    id, name, district, gx, gy, w, d,
    loc, files, tests, api,                       // fanin is derived — do not author it
    one, what, built,                             // what/built: paragraphs split on \n\n
    kind:'authored'|'generated'|'vendored',
    entries: [{ g:'group', l:[{ m:1, s:'signature()', d:'file:line' }] }],   // m:1 mutating
    quirks:  [{ t:'claim', s:'file.ts:88', q:'verbatim source ≤12 lines' }],
    legacy: true,                                 // dormant — renders as a ruin
  }],

  edges: [{ from, to, label, cite, kind:'read', via:[[x,y],…] }],
  flows: [{ id, name, sub, steps:[{ from, to, t:'html', k:'CALL'|'ENTRY'|'GAP', cite }] }],
};
```

`what`, `built`, `quirks[].t` and `steps[].t` accept inline `<code>` and `<b>`. Everything else
is escaped. A flow step's `to` may be `null` for a hop that stays inside one building.

## Budget

**Coverage is not negotiable; depth is.** Every module in your manifest gets a building, a
one-liner, and a `what`. What scales with repo size is how deeply you read each one — not how
many you skip.

| repo | files read per module | edges kept | prose |
|---|---|---|---|
| < 300 files | up to 12 | all internal | full for every module |
| < 3000 files | up to 12 | top 150 by weight | full for the top 20, two sentences for the rest |
| ≥ 3000 files | up to 8 | top 200 by weight | full for the top 15, two sentences for the rest |

Never read a file over 1,500 lines in full — use `sed -n '400,460p'` around the region you cite.
One census pass, never a per-file loop. If you hit a cap, say so on the page.

## What this cannot do, and should say so

Position is **not** measured — the layout places buildings, not the dependency graph. Wires are
a **lower bound**: dynamic dispatch, dependency injection, event buses and anything crossing a
process boundary leave little textual trace. Prose and sharp edges vary between runs even when
the measurements do not. Put all three in `unknowns` rather than implying a rigour you do not have.
