# exec-prompts

## Overview

`make-prompts`로 생성된 단계별 프롬프트 파일을 읽고, 작업 내용과 방법을 분석하여 agent teams를 구성하고 실행한다.

지원 bundle 경로:
- 단독 호출의 기존 경로: `to_do_prompts/{feature_name}_prompts/`
- project-run의 활성 run 경로:
  `.loop-engine/runs/{run_id}/prompt-bundles/{feature_name}_prompts/`

호출자가 `bundle_dir` 인자를 제공하면 해당 경로를 유일한 입력으로 사용한다.
특히 project-run은 make-prompts 완료 보고의 `bundle_dir`를 그대로 전달해야 한다.

**핵심 원칙:** 프롬프트는 실행 전에 명시적으로 작성되어 있어야 한다. 이 스킬은 생성이 아닌 실행 전담이다.

## 전제 조건

스킬 호출 전에 반드시 충족:
1. 선택된 `{bundle_dir}` 디렉토리에 실행할 프롬프트 파일이 존재
2. `main_*.md` 파일이 entry point로 존재
3. 각 STEP의 **실행 프롬프트** 블록이 작성 완료 상태

## 실행 흐름

```
STEP 1: 프롬프트 파일 읽기
  └─ 선택된 `{bundle_dir}/` 전체 스캔
  └─ main_*.md 에서 단계 구조 파악
  └─ 각 step 파일(있으면) 로드

STEP 2: 작업 분석
  └─ 각 단계의 목표, 대상, 의존성 파악
  └─ 병렬 실행 가능 단계 식별
  └─ 단계별 전문성 요구사항 분류

STEP 3: Agent Team 구성
  └─ 각 단계에 적합한 agent 유형 결정
  └─ 병렬 가능 단계는 동시 dispatch

STEP 4: 순차/병렬 실행
  └─ 의존성 순서 준수
  └─ 각 단계 완료 기준 검증
  └─ 완료된 단계 체크리스트 업데이트

STEP 5: 완료 보고
```

## STEP 1: 프롬프트 파일 읽기

실행할 `{bundle_dir}`를 다음 우선순위로 특정한다.
1. 호출자가 `bundle_dir`를 명시한 경우 → 해당 경로만 사용한다. legacy 폴더를 재탐색하거나
   사용자 선택을 요청하지 않는다.
2. `bundle_dir`가 없는 단독 호출 → `to_do_prompts/` 하위에서 실행할
   `{feature_name}_prompts/` 폴더를 특정한다. 사용자가 명시한 경우 해당 폴더를 사용하고,
   명시하지 않은 경우에만 목록을 나열하여 선택을 요청한다.

폴더 스캔 순서:
1. `main_*.md` 파일 우선 로드 (entry point)
2. `step_NN_*.md` 또는 `group_*.md` 파일 로드
3. 전체 단계 수, 의존성 그래프, 대상 파일 목록 파악

파일이 없으면 즉시 중단:
```
실행 불가: {bundle_dir}/main_*.md 파일 없음.
/make-prompts 먼저 수행 후 재시도.
```

### STEP 1-A: 구조화 필드(step_id/depends_on[]) 존재 시 우선 처리 (필드 존재 여부로 분기)

step 레코드에 `step_id`/`depends_on[]` 필드가 존재하는 경우, 실행 순서와 병렬 가능 여부를
**LLM 추론이 아닌 `loop-engine task-graph` CLI 결과로 결정론적으로 확정**한다:

1. 각 step의 `step_id`/`depends_on[]`을 모아 JSON 배열 파일(steps-file)로 구성한다.
   예: `[{"step_id": "A", "depends_on": []}, {"step_id": "B", "depends_on": ["A"]}]`
2. 실행 순서 확정:
   ```bash
   loop-engine task-graph order --steps-file <steps-file>
   ```
   - 성공 시 stdout에 JSON 배열(예: `["A", "B"]`)로 순서가 출력된다 — 이 순서를 그대로 신뢰한다.
   - 순환 의존이 있으면 non-zero exit code + stderr에 cycle 경로가 출력된다 — 이 경우 즉시 중단하고
     사용자에게 보고한다(임의로 순서를 추정하여 진행하지 않는다).
3. 각 시점의 병렬 가능 STEP 집합 판단:
   ```bash
   loop-engine task-graph ready --steps-file <steps-file> --completed <완료된 step_id 콤마 구분>
   ```
   - stdout에 지금 당장 동시 dispatch 가능한 step_id 목록이 JSON 배열로 출력된다.
   - STEP 완료마다 `--completed` 값을 갱신하여 재호출, 다음에 병렬 실행 가능한 집합을 다시 확인한다.

**필드 존재 여부로 분기**: `step_id`/`depends_on[]` 필드가 없는 레거시 프롬프트 파일(현재 대부분의
기존 `to_do_prompts/*` 파일)은 위 절차를 적용하지 않고 STEP 2의 기존 방식(LLM이 `**다음 단계**:`
필드와 대상 파일 겹침을 판단하여 순서/병렬 여부를 추론)을 그대로 유지한다 — 하위 호환 원칙, 기존
절차를 삭제하거나 대체하지 않는다.

## STEP 2: 작업 분석

`step_id`/`depends_on[]` 필드가 없는 레거시 프롬프트 파일에 적용(필드가 있으면 STEP 1-A 결과를
우선 신뢰 — 필드 존재 여부로 분기).

각 단계에서 추출할 정보:

| 항목 | 추출 위치 | 용도 |
|------|---------|------|
| 목표 | `**목표**:` 필드 | agent brief 작성 |
| 대상 파일/모듈 | `**대상**:` 필드 | agent scope 제한 |
| 실행 프롬프트 | 코드블록 내용 | agent에 전달할 지시문 |
| 완료 기준 | `**완료 기준**:` 체크리스트 | 검증 조건 |
| 의존성 | `**다음 단계**:` 필드 | 실행 순서 결정 |

병렬 실행 판단 기준:
- 대상 파일이 겹치지 않음 → 병렬 가능
- 의존성 없음 (선행 단계 불필요) → 병렬 가능
- 공유 상태(DB, 환경변수, 설정파일) 없음 → 병렬 가능

## STEP 3: Agent Team 구성

### 모델 강제 규칙 (MANDATORY)

**모델 강제 규칙** — `engine` 인자 미지정 또는 `engine=claude`(기본값): 모든 sub-agent는
`model: "sonnet"` 강제(기존 규칙 그대로). `engine=codex`: 아래 "STEP 3-C: Codex 실행 경로"를
따른다.

`engine` 미지정 또는 `engine=claude`(기본값) 경로 — 모든 sub-agent는 반드시 `sonnet` 모델을
사용한다. 예외 없음.

Agent tool 호출 시 항상 `model: "sonnet"` 명시:
```
Agent(
  subagent_type=...,
  model="sonnet",   ← 항상 포함, 생략 금지
  prompt=...
)
```

이 규칙은 단계 복잡도, agent 유형, 병렬/순차 여부와 무관하게 전체 적용된다.

### STEP 3-C: Codex 실행 경로 (engine=codex일 때만 적용)

`engine=codex`로 호출된 경우, STEP 3의 sub-agent dispatch를 Agent tool 대신 아래 절차로
대체한다(worktree/registry/heartbeat 등 기존 인프라는 그대로 재사용, 실행 주체만 codex CLI로
전환).

1. **worktree 경로 확보** — `project-run.md`가 이미 만든 `loop-engine/{name}/run-v{N}` worktree를
   그대로 사용한다(신규 격리 불필요).
2. **registry/heartbeat 기록** — dispatch 대상 step이 확정되면(STEP 1-A `task-graph ready`
   결과 또는 STEP 2 레거시 추론 결과), 각 step마다:
   ```bash
   loop-engine registry add --project {name} --agent-id {id} --parent {parent} \
     --depth {n} --task-scope {scope} --engine codex
   loop-engine heartbeat touch --project {name} --agent-id {id}
   ```
   (기존 STEP 3 registry/heartbeat 절차와 동일 — orchestrator가 그대로 기록, 엔진 전환과 무관.
   `--engine codex`는 필수 — run loop 단계에서 `--engine claude` 또는 미지정 시
   `registry.py`의 `ENGINE_STAGE_RULES` 검증에서 `engine_stage_mismatch`로 거부됨)
3. **codex exec 백그라운드 시작** — `run_in_background: true`로 시작한다. 매 호출마다 모델/
   effort를 명시적으로 지정:
   ```bash
   codex exec \
     -C "{worktree_path}" \
     -m gpt-5.6-terra \
     -c model_reasoning_effort="ultra" \
     -s workspace-write \
     --json \
     -o "{step_output_dir}/last-message.txt" \
     "{step 실행 프롬프트 — 코드블록 내용 그대로, 목표 필드 아님}" \
     < /dev/null \
     > "{step_output_dir}/events.jsonl" \
     2> "{step_output_dir}/events.stderr.log"
   ```
   (2026-08-19 실측 근거로 조정됨 — 원안의 `--full-auto`/`2>&1`/stdin 미지정 3곳을 아래와 같이
   변경. `codex-cli 0.145.0` 기준 실제 동작 확인, 추측성 수정 아님.)
   - `-s workspace-write` (← `--full-auto`에서 변경): 실측 결과 `--full-auto`는 이 버전에서
     **deprecated**로, 호출 시 매번 `warning: `--full-auto` is deprecated; use `--sandbox
     workspace-write` instead.`가 stderr에 출력된다. `-s workspace-write`만 단독 사용해도 워크트리
     내부 파일 생성/셸 명령 실행이 승인 프롬프트 없이 완료됨을 실측으로 확인(파일 생성 1건, 셸 명령
     실행 1건 모두 프롬프트 없이 성공) — `--full-auto`와 동등한 자율 실행 효과를 얻으면서 deprecation
     경고도 피한다. RULES.md "HLT-1~6이 아니면 확인 요청 금지" 원칙과 이중 게이팅되지 않게 하는
     역할은 그대로 유지된다.
   - `< /dev/null` (신규 추가, 필수): stdin을 명시적으로 닫지 않으면 codex exec가 시작 시 항상
     "Reading additional input from stdin..." 상태로 진입하는데, 호출 경로에 따라 이 지점에서
     **무한 대기(hang)가 재현됨**을 실측으로 확인했다(포그라운드 명령이 120s 타임아웃 후 자동으로
     백그라운드 이동된 경로에서 15초 이상 대기해도 JSON 이벤트가 전혀 출력되지 않고 멈춰 있었음 —
     강제 kill로 종료). 반대로 처음부터 `run_in_background: true`로 시작한 호출이나 `< /dev/null`을
     명시한 호출은 즉시 정상 완료됨. 즉 stdin 상태가 호출 경로마다 달라 결과가 비일관적이므로,
     `< /dev/null`을 빠짐없이 명시해 항상 즉시 EOF를 주는 방식으로 고정한다.
   - `2> "{step_output_dir}/events.stderr.log"` (← `2>&1`에서 변경): `2>&1`로 합치면 위
     "Reading additional input from stdin..." 안내 문구(및 `--full-auto` 사용 시의 deprecation
     경고)가 `events.jsonl`에 그대로 섞여 들어가 JSON 파싱이 깨진다(실측: 첫 줄이 `warning: ...`
     또는 `Reading additional input...` 텍스트로 시작해 `json.loads` 실패). stdout(`--json`
     이벤트)과 stderr(안내/경고 문구)를 별도 파일로 분리해야 `events.jsonl`이 순수 JSONL을
     유지하고, STEP 3-C 4번의 라인 수 기반 폴링/파싱이 안전해진다.
   - `-o`: 완료 기준 검증에 쓸 최종 메시지를 별도 파일로 받는다(STEP 4와 연결). 이 부분은 실측
     결과 원안과 동일하게 유지(정상 동작 확인됨).
   - `--json`과 승인 자동화 플래그(`--full-auto` 구버전 표기든 `-s workspace-write` 신버전
     표기든) 동시 지정은 실측상 상호배제 없이 정상 동작함 — 미지원 조합 아님.
4. **heartbeat/orphan-check 대체** — 백그라운드 task를 60s 주기로 폴링하며, `events.jsonl`에
   새 라인이 추가되어 있으면(=codex가 살아서 진행 중) 그때마다
   ```bash
   loop-engine heartbeat touch --project {name} --agent-id {agent_id}
   ```
   재호출한다. 새 라인 없으면 heartbeat 안 찍음 — 기존 `registry orphan-check --timeout 600`이
   그대로 재사용 가능해짐(orphan_detector/timeout_watchdog 로직 변경 없음).
5. **완료 판정** — 백그라운드 task 종료 확인(또는 `events.jsonl`의 종료 이벤트) →
   ```bash
   loop-engine registry update --project {name} --agent-id {id} --status completed
   ```
   `-o`로 받은 `last-message.txt`를 STEP 4(완료 기준 검증)의 검증 대상으로 사용.
6. **UTR(즉시 중단) 신호** 발생 시: 실행 중인 codex 백그라운드 task를 중단시키고
   `registry update --status cancelled`로 마킹(대상만 Agent tool 프로세스에서 codex 백그라운드
   task로 바뀜, 기존 UTR 절차와 동일 원칙).

### 단계 특성에 따른 agent 유형 매핑

| 단계 특성 | Agent 유형 | 모델 |
|---------|-----------|------|
| 1~2 파일 수정, 명확한 스펙 | `cavecrew-builder` | sonnet (강제) |
| 코드 분석/탐색 | `cavecrew-investigator` | sonnet (강제) |
| 멀티파일, 통합 작업 | `claude` (general) | sonnet (강제) |
| 아키텍처/설계 판단 | `Plan` agent | sonnet (강제) |
| 완료 후 리뷰 | `cavecrew-reviewer` | sonnet (강제) |

Agent brief 작성 규칙:
- 세션 히스토리 전달 금지 — 해당 단계의 실행 프롬프트만 전달
- 대상 파일/모듈 명시적 scope 포함
- 완료 기준 포함

## STEP 4: 실행

매 턴 시작 시 UTR 신호(사용자 발화) 대기 여부를 최우선으로 확인한다(project-run.md와 동일 원칙).

### 병렬 실행

의존성 없는 단계는 단일 메시지에 복수 Agent tool call로 동시 dispatch:

```
[STEP 2, STEP 3 병렬 실행 — 대상 파일 독립적]
Agent(cavecrew-builder, brief=step_02_내용)
Agent(cavecrew-builder, brief=step_03_내용)
```

### 순차 실행

선행 단계 완료 확인 후 다음 단계 진행:

```
STEP 1 완료 기준 검증
  → 통과 시: STEP 2 dispatch
  → 실패 시: 원인 보고 후 중단 (사용자 확인 요청)
```

### 완료 기준 검증

각 단계 완료 후:
1. `main_*.md`의 해당 STEP 체크리스트 항목 확인
2. 체크리스트 전부 충족 → 다음 단계 진행
3. 미충족 항목 발견 → 해당 agent 재dispatch (1회 한정)
4. 재시도 후도 미충족 → 사용자 보고 후 중단

## STEP 5: 완료 보고

```
## exec-prompts 완료

실행된 단계: N / N
  ✅ STEP 1: {제목} — 완료
  ✅ STEP 2: {제목} — 완료
  ⚠️  STEP 3: {제목} — 완료 (우려사항: ...)

총 사용 agent: N개
병렬 실행: N단계

다음 권장 작업:
  - /adversarial-review (교차 검증 필요 시)
  - /commit (변경사항 커밋)
```

## 금지 사항

- sub-agent 호출 시 `model: "sonnet"` 생략 금지
- 선택된 `{bundle_dir}`의 프롬프트 파일 내용을 직접 수정하지 않음
- 실행 프롬프트를 임의 변경하여 실행하지 않음
- 완료 기준 미검증 상태로 다음 단계 진행하지 않음
- Critical 이슈 발생 시 사용자 확인 없이 계속 진행하지 않음
- BLOCKED 상태가 아닌데 사용자에게 "계속 진행할까요?" 묻지 않음
- `engine=codex`일 때 `-s workspace-write` 생략 금지(승인 프롬프트 이중 게이팅 발생 — 2026-08-19
  실측으로 `--full-auto`는 deprecated 확인, `-s workspace-write`로 대체)
- `engine=codex`일 때 `-m`/`-c model_reasoning_effort=` 생략 금지(전역 `~/.codex/config.toml`
  기본값에 암묵적으로 의존하게 됨)
- `engine=codex`일 때 stdin을 `< /dev/null`로 닫지 않고 실행 금지(호출 경로에 따라 "Reading
  additional input from stdin..." 상태에서 무한 대기하는 현상을 실측으로 확인)
- `engine=codex`일 때 stdout/stderr를 `2>&1`로 합치지 않음(경고/안내 문구가 `events.jsonl`에
  섞여 JSON 파싱이 깨지는 것을 실측으로 확인 — 별도 `*.stderr.log` 파일로 분리)

## Common Mistakes

| 실수 | 수정 방법 |
|------|---------|
| `main_*.md` 없이 `step_*.md`만 로드 | 항상 main 파일부터 시작 |
| 의존성 있는 단계를 병렬 실행 | 의존성 그래프 재확인 |
| 실행 프롬프트 대신 목표 필드를 agent에 전달 | 코드블록 내 프롬프트만 전달 |
| 완료 기준 없이 다음 단계 진행 | 체크리스트 항목 모두 확인 |
| `depends_on[]` 필드 무시하고 서술문(`**다음 단계**:` 필드)만 참조 | `step_id`/`depends_on[]` 필드가 있으면 `task-graph order` 결과를 우선 신뢰 |
| `engine=codex`에서 `-s workspace-write` 생략(또는 deprecated `--full-auto` 사용) | 승인 프롬프트 이중 게이팅 발생 / deprecation 경고 발생 — `-s workspace-write` 반드시 포함 |
| `engine=codex`에서 `-m`/`-c` 생략, 전역 config.toml 의존 | 매 호출 명시적으로 지정 |
| `engine=codex`에서 stdin 미차단(`< /dev/null` 생략) | "Reading additional input from stdin..." 상태에서 무한 대기 재현됨 — 반드시 `< /dev/null` |
| `engine=codex`에서 `2>&1`로 stdout/stderr 병합 | `events.jsonl`에 비-JSON 경고 라인 섞여 파싱 깨짐 — stderr는 별도 파일로 분리 |
