# ADR（Architecture Decision Record）作成

## なぜADRを書くか

このプロジェクトは複数人（社内有志）が関わり、会話ベースでいろいろな意思決定が積み重なっていきます。決定した本人はその場では経緯を覚えていますが、数か月後に他の人（あるいは未来の自分）が「なぜこうなっているのか」を知りたくなったとき、会話ログやPRの差分だけでは背景が追いにくいことがあります。ADRは、決定そのものではなく「なぜその決定に至ったか」を短く残すための記録です。

## いつ書くべきか

次のような特徴を持つ決定はADR化を検討してください。すべてに当てはまる必要はありません。

- 複数の選択肢を比較して、どれか一つを選んだ（他の選択肢を捨てた）
- 後から覆すとやり直しのコストが大きい（ファイル構成、ライブラリ・ツールの選定、運用フロー、公開範囲など）
- 将来「なぜこうなっているんだっけ」と聞かれそうな判断
- 賛否や代替案の余地があった（一択しかなかった作業には使わない）

逆に、次のようなものはADR不要です。

- 単一ファイル内の実装の詳細（変数名、ロジックの微修正など）
- 明らかにバグである不具合の修正
- 後から簡単にやり直せる、影響範囲の小さい選択

判断に迷う場合は、無理に作らず「ADRにするほどの決定かどうか分かりませんが、念のため確認します」とユーザーに聞いてください。

## 会話の中でADRを提案するタイミング

ユーザーから明示的に依頼されていなくても、会話の中で上記に当てはまる決定が確定した直後（実装に入る前後どちらでも構いません）に、次のように一言添えてください。

> 「〇〇という決定になりましたが、これはADRとして残しておきましょうか？」

ユーザーが乗り気でなければそれ以上は勧めず、会話を続けてください。逆にユーザーが最初から「ADRを書いて」と頼んできた場合は、この確認は省略して次の手順に進んで構いません。

## ファイルの配置・命名

- 置き場所: `docs/adr/`
- ファイル名: `NNNN-slug-in-english.md`（4桁の連番＋英語のスラッグ）。連番は`docs/adr/`内の既存ファイルを`ls`して次の番号を採番してください。既存ADRを書き換えて番号を詰め直すことはしないでください。
- 決定を覆す・変更する場合は、古いADRの記述を消さずに残したまま、ステータスを「廃止（後継: ADR NNNN）」に更新し、新しいADRを追加してください。ADRは「今の正解集」ではなく「決定の履歴」として扱います。

## テンプレート

内容は日本語で書いてください（このリポジトリの言語規約に合わせる）。

```markdown
# ADR NNNN: <決定のタイトル>

- ステータス: 提案 | 承認 | 却下 | 廃止（後継: ADR NNNN）
- 日付: YYYY-MM-DD

## コンテキスト

<なぜこの決定が必要になったか。背景・制約・前提となる状況を書く>

## 決定

<何を決定したか。結論を簡潔に書く>

## 検討した代替案

<比較した他の選択肢と、それらを採らなかった理由。なければ「特になし」>

## 結果・影響

<この決定によって何が変わるか。今後発生しうるトレードオフや制約>
```

## 手順

1. 上記の基準でADR化する決定内容を1つに絞り、要約する
2. `docs/adr/`内の既存ファイルを確認し、次の連番を採番する
3. 上記テンプレートに沿って`docs/adr/NNNN-slug-in-english.md`を作成する。他のADRから状況が変わって古いものを置き換える場合は、そのADRのステータスも更新する
4. 書いた内容をユーザーに見せ、事実誤認や書き漏れがないか確認する
5. コミット・PR化は`commit-and-pr`スキルを使う（手順の重複を避けるため、ここでは繰り返さない）
