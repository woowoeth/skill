# 沟通函撰写

## 处理要求
1. 复用对话中已有原文、涉事企业、材料与诉求。只在原文缺失或主体无法确定等关键问题阻碍任务时，用 ask_user 一次询问必要信息；不重复确认。
2. 用 search_knowledge_base / web_search 核查关键数据与事实，区分属实、不属实和存疑。比对主体、时间、指标口径和单位，保留出处。
3. 逐项调用 record_verification 保存原始主张、主体、时间、结论和引用；引用使用检索返回的 source_id 及完全对应的原文 quote。先形成核查结论再写正文。承认有依据的问题，仅澄清已证实的错误；资料不足时写明待核实项，不把存疑写成失实。
4. 政策与法律依据只有在查到适用于本案的权威来源后才引用。没有证据，不指控发布者恶意、节点炒作或造成社会危害。
5. template.txt 仅为结构参考，方括号内容必须按本案填写或删除，不是事实材料。不得套用其他案件的数字、指控或诉求。
6. 按用户目标提出更正、补充说明或其他有事实依据的处理请求。只有用户提出下架诉求且已核实依据支持时，才写下架请求。
7. 调用 save_communication_letter(title, opening, sections, closing)。每个 section 填写已保存的 verification_id 和对应 response；工具会生成完整正文，自动附上原始主张、核查结论、证据原文及出处。存在存疑项时自动标为待核实草稿。opening、response、closing 不能加入未核实的事实或与记录相反的断言。

## 正文结构
- 标题：沟通函（证据不充分时标注「待核实草稿」）。
- 抬头：尊敬的贵平台。
- 开头：说明企业、报道标题和沟通目的，不预设报道失实。
- 正文：按「原表述 → 核查结论 → 具体依据 → 建议更正内容」逐项展开。
- 结尾：提出与证据和用户目标相符的处理诉求，语气专业克制。
- 引用出处：列出实际使用的文件名称和片段位置，或网页标题及完整 URL。
- 待补充事项：如有未核实内容，明确所缺材料，不以猜测补全。
