# 报销单生成器

把一个文件夹的发票(PDF + 照片)整理成一份打印即合规、便于做账和税务备查的报销单包。

## 工作流(交互式,按顺序)

### 0. 整理与规范化发票文件(做报销单前必做)

收到一批杂乱命名的发票/照片,先统一改名 + 按开票月归档,再进后续步骤。这步让查重、核对、归档全程有稳定锚点。

**命名格式**:`日期_收支_科目_对方_金额CNY_票号尾8位.pdf`
例:`2025-06-03_支_交通费_某出行平台_1234.56CNY_88001234.pdf`

字段规则:
- 分隔符:日期内 `-`,字段间 `_`
- 日期 = **开票日期**(`YYYY-MM-DD`),不是付款日/所属期
- 收支:出项=`支`,进项=`收`(单字)
- 金额:发票**真实价税合计**,两位小数,**禁千分符**(逗号破坏 CSV/脚本/跨平台)
- 币种:ISO 4217 `CNY`/`USD`,**禁 ￥/$**(¥ 日元人民币共用有歧义;$ 触发 shell 变量展开)
- 票号尾8位:查重键 + 唯一锚点,保证不撞名
- 对方:销售方简称(`北京示例餐饮有限公司`→`示例餐饮`)
- 科目:费用类别(餐饮/交通费/云服务费/办公服务费…),沿用业务口径,不擅自重分类

**必读真值**:旧文件名金额常是四舍五入的(`687元` 实为 `¥687.16`),改名前**逐张取真实价税合计 + 票号**,不能信旧名:
- PDF:`mcp__pymupdf4llm__convert_pdf_to_markdown`(文本提取,省开销;`image_path` 指临时目录免污染归档)。这步顺带为第 2 步省去重复解析。
- **照片(无文本层)**:用 Read 工具视觉识别出发票号/开票日期/销售方/价税合计/类别,再按同规范改名,扩展名保留 `.jpg/.png`。金额与票号按审查纪律人工复核。

**分月归档**:按开票月建子文件夹(`2025-06/` 等);一票一月不拆,跨月行程的滴滴票归到开票月。
**附件配对**:滴滴行程单等附件用 `_行程单` 替代票号位(`..._1234.56CNY_行程单.pdf`),与对应发票同前缀紧邻排序;凭金额精确配对,别凭文件名 A/B 猜。

完整规范与踩坑见 memory `invoice-naming-convention`(finance 项目)。整理完再进第 1 步。

### 1. 收集必要信息(用 AskUserQuestion 提问,已知的跳过)

- **报销主体**:公司全称 + 统一社会信用代码(这是发票购买方,也用作买卖方区分的 buyer-hint)
- **报销人 / 部门**
- **费用所属期 / 申请日期 / 报销单号**(单号建议 `BX-YYYY-MM-DD-NN`)
- **支付方式**:个人垫付后返还 / 对公直付

不要一次问太多;主体和报销人最关键,其余可用合理默认并在交付时说明。

### 2. 提取发票字段

```bash
python scripts/extract.py --src "<发票文件夹>" --out "<工作目录>" --buyer-hint "<公司简称>"
```

产出 `<工作目录>/parsed.json` = `{invoices, photos, itineraries}`,并渲染逐票图到 `_inv_img/`。

- **金额用中文大写解析**(`rmblib.cn_capital_to_num`),不是 `max(¥)` —— 发票有负数折扣行,大写是唯一权威来源。
- **照片(photos[])无文本层**:逐张用 Read 工具**视觉识别**,读出发票号/开票日期/销售方/价税合计/税率/类别,补成与 PDF 发票同结构的记录。按审查纪律,金额和发票号必须人工复核。
- 把 PDF 发票 + 照片识别结果合并成一个 `invoices.json` 数组(供第 5 步)。

### 3. 核对(必做)

把解析出的发票列成表给用户核对:日期 / 销售方 / 类别 / 价税合计 / 税率。逐张金额与文件名或票面交叉验证。**金额解析失败的行(⚠)必须人工补**。

### 4. 用途说明 + 滴滴行程单

- **用途说明**:发票上没有,需推断或问用户。推断值标记 `draft:true`(报销单里渲染成灰色"待核对")。事由须真实——这是税务最看重的字段。
- **滴滴等汇总发票**:必须有配套**行程单**。若 `itineraries[]` 有对应行程单:
  ```bash
  python scripts/itinerary.py --itin "<行程单.pdf>" --out "<工作目录>" --invoice-total <发票金额> --city "<城市>"
  ```
  - 校验 **行程单合计 = 发票价税合计**(不一致要查)
  - 生成**紧凑重制版**(原版常 7+ 页 → 2-3 页),路径写入对应发票行的 `itin_pdf`,`itin_n` = 笔数
  - 输出**异常扫描**:住宅/通勤、商场、餐厅、周末、深夜笔数 + 公私拆分金额
  - 若私人特征占比高(高管日常出行常见),**如实告知用户**:这部分是通勤/私人消费,作公司交通费报销有企业所得税调增 + 个税风险。详见 `references/compliance.md` 与 `references/vehicle-policy-template.md`。
  - 滴滴原版 PDF 保留作原件存档,重制版仅进打印包。

### 5. 生成报销单包

```bash
python scripts/build_packet.py --config "<config.json>" --data "<invoices.json>" --out "<工作目录>"
```

产出 `报销单.pdf`(封面 + 分析合规页 + 逐票页,滴滴页后拼接紧凑行程单)+ `发票查重台账.csv`。脚本返回页数、合计、查重结果(重复发票号)、类别小计。

config.json / invoices.json 字段见各脚本头部 docstring。invoices.json 每行关键字段:
`file, inv_no, date, seller, total, rate, cat, purpose, img, draft(默认true), itin_pdf(可选), itin_n(可选)`

### 6. 验证与交付

- 用 pymupdf 渲染封面页和任一逐票页为 PNG,Read 检查版式(无跨页截断、日期不换行、发票图清晰)。
- **窄列/卡片里的中文或数字串必须 `white-space:nowrap`**——这是反复踩的坑(总表日期、KPI 卡都犯过)。
- 交付:报销单.pdf + 查重台账.csv;若涉及滴滴私人占比或大额项,附合规提示。

## 合规要点(关键,勿略)

详见 `references/compliance.md`。核心:

- 电子发票**纸质打印件不能单独入账**,必须同时归档**电子原件**;按发票代码+号码查重防重复报销。
- 报销单硬核字段:报销部门、日期、**真实用途/事由**、金额大小写、经办人+审核人签字、附件张数。
- 真伪查验:全国增值税发票查验平台 inv-veri.chinatax.gov.cn。
- 高管/员工通勤及私人用车由公司报销 = 变相工资薪金,应代扣个税;走《用车制度》定性为补贴是合规路径,但不免个税。模板见 `references/vehicle-policy-template.md`。

## 环境

- 依赖:`pymupdf`(fitz)、Chrome 或 Edge(headless 渲染 PDF,`rmblib.find_chrome` 自动探测)。
- Windows + Git Bash:临时脚本不要命名为 `inspect.py`/`json.py` 等标准库同名,会 shadow 导致 pymupdf import 崩溃。
