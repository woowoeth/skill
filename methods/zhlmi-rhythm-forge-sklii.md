# 节奏锻造师

把一首歌变成能真正上手打的网页音游。

核心不是"把音符对齐鼓点"——那是最容易的一步。真正的工作量在**可玩性约束求解**：
让谱面符合人类双拇指的物理操作极限，否则生成的谱面看着漂亮却根本打不出来。

## 何时使用

用户提供音频文件并希望做成音游、生成谱面、或提到"节奏锻造/音游/音乐游戏/谱面"时。
用户也可能只说"用这首歌试试"——如果上文已在做音游，直接走流程。

## 🔴 检查点（红灯，不可跳过）

### 情况 A：用户要音游但没给音频

用户说"做个音游""节奏锻造""把这首歌做成游戏"等触发词，但**没有附带音频文件**时，
**必须停下来**，不要开始跑任何脚本。提醒用户：

> 需要一首音频文件才能生成音游。把 mp3 / m4a / wav / flac 等格式的音乐文件发过来就行，
> 格式不限，长短不限。

等到用户确实上传了音频文件再继续。

### 情况 B：用户给了音频，开始前检查并提醒

收到音频文件后，**先跑 `ffprobe` 检查**，然后按结果提醒用户：

| 检查项 | 条件 | 提醒内容 |
|---|---|---|
| 时长过长 | > 7 分钟 | 文件会偏大（base64 内嵌约每分钟 0.6 MB），建议降码率或裁副歌。问用户是否接受 |
| 时长过短 | < 15 秒 | 谱面太短没意思，确认用户是否只要这么短 |
| 码率很高 | > 256k | 会内嵌原始大小，建议用默认 AAC 64k 压缩。说明音游只需节拍参考，听感损失很小 |
| 格式异常 | ffprobe 报错 | 告知用户文件可能损坏或格式不支持，请换一个 |
| 多声道 | channels > 2 | 不影响（会自动降混为单声道），无需提醒 |

检查通过后，**简要告知用户即将做什么**（编码 → 分析 → 校验 → 打包），
然后直接开始，不需要等用户再次确认——他要的东西已经明确了。

### 情况 C：歌曲偏柔（起音点偏少）

谱面生成后，如果检测到的起音点明显偏少（每秒 < 2.5 个），
**主动告知用户**三档密度会比一般歌曲低一档左右，这是歌本身的性质不是分析出错。
建议提高 `--hard-extra`（可到 0.5~0.6）补偿，等用户决定。

## 快速开始

一条命令走完全流程（编码 → 成谱 → 校验 → 打包）：

```bash
python3 scripts/forge.py <音频文件> --title "歌名" --artist "演唱者"
```

产出一个零依赖的单文件 HTML。

常用选项：

| 选项 | 说明 | 默认 |
|---|---|---|
| `--title` / `--artist` | 歌名与演唱者，写进页面标题和菜单 | 取文件名 |
| `--bitrate` | 音频码率(k) | 64 |
| `--samplerate` | 采样率(Hz) | 32000 |
| `--hard-extra` | 困难档额外加密比例 0-1 | 0.30 |
| `--density` | 整体密度缩放，>1 更密 | 1.0 |
| `--out` | 单文件输出路径 | 音频同级目录 |
| `--keep` | 保留中间文件目录，便于手动微调 | 关 |

## 执行流程

1. **前置检查**：按上方检查点 B 的表格跑 `ffprobe` 并处理异常。
2. **跑流水线**：`forge.py`。它会逐步打印每档音符数、密度、长条数和校验结果。
3. **报告数据**：把三档的音符数/密度/长条数列成表给用户看，让他判断难度是否合适。
4. **给可点链接**：将产出移到 `/var/minis/workspace/` 下，用 Markdown 链接给出。
   （Minis 环境下用 `--out /var/minis/workspace/<歌名>-音游.html` 让 forge.py 直接输出到该目录。）
5. **按反馈调参**：见下方"调参手册"。

流水线任一步失败会立即中止，不产出半成品。
若中途崩溃（ffmpeg 被 kill、numpy 段错误等），告知用户具体错误信息，
不要只说"失败了"--把 forge.py 的最后输出贴出来帮助排查。

## 关键设计：双拇指可玩性模型

这是本 Skill 最不容易复现的部分。手位假设：**轨1、2 属左手拇指，轨3、4 属右手拇指**。
一个长按会占住**整只手**，由此推导出五条硬规则（全部在生成阶段消解，不靠运行时补救）：

| 规则 | 说明 |
|---|---|
| 同轨冲突 | 长按期间该轨不能有点按——手指还压着 |
| 同手冲突 | 长按期间同一只手的另一条轨也不能有点按 |
| 区间重叠 | 同一只手不能同时压两个长按 |
| 同轨过密 | 同一轨两次长按间隔 ≥ 1.2s，否则手指刚松又要压回 |
| 同手过密 | 同一只手两次长按间隔 ≥ 0.55s |

长按前后各留保护余量（起手前 140ms、松手后 180ms）给手指转移。
冲突音符**优先搬到空闲的另一只手**，搬不动才丢弃，尽量不损失节奏信息。

**每次改动谱面生成逻辑后必须跑校验**：

```bash
python3 scripts/validate.py beatmap.js
```

五类冲突必须全为 0。这是硬性验收标准，不是可选检查。
（`validate.py` 在工作目录中运行，工作目录由 `forge.py --keep` 保留。）

## 调参手册

用户反馈 → 改哪里（都在 `scripts/beatmap.py` 顶部的 `DIFFS`）：

| 反馈 | 处理 |
|---|---|
| 太简单 / 太难 | 调 `gap`（最小间隔，越小越密）。也可整体用 `--density 1.2` |
| 困难档不够压 | 提高 `--hard-extra`（切分音填充比例）。慢歌可到 0.5~0.6 |
| 长按太少 | 提高对应难度的 `hold` 概率 |
| 双押太少 | 提高 `chord` |
| 下落太快/太慢 | 调 `speed` |
| 音符挤在中间两轨 | 检查 `assign_lanes`——已用中位数相对划分 + 计数配平，正常应在 22~28% |

**慢歌注意**：抒情慢歌起音点天然少（实测某慢歌 466 个 vs 某快歌 730 个），
三档密度会整体偏低。这是歌本身的性质。要补偿就提高 `--hard-extra`，
并主动告知用户原因，不要让他以为分析出错。

## 游戏侧规则（已实现，改动时勿破坏）

- **判定窗口**：PERFECT ±55ms / GREAT ±105ms / GOOD ±165ms / 超 195ms 判 MISS
  （移动端触屏有 50-80ms 延迟，窗口不能照搬 PC 端的 ±45ms）
- **长按计分**：头尾各算一个判定点。完成率 ≥ 80% 视为完整成功（Perfect），
  50%~80% 部分成功（Good，不断连击），< 50% 判 Miss 并断连击。
  完全没按到的长条头尾各判一次 Miss（保证判定点总数一致，不会因为"按了头反而更亏"）
- **准确率**：加权 Perfect 1.0 / Great 0.85 / Good 0.5 / Miss 0
  （参考 IIDX 权重，Great 0.7 过低会导致触屏延迟下大量 Great 拖垮准确率）
- **等级**：SSS(全 Perfect) > SS(98%) > S(93%) > A(85%) > B(75%) > C(60%) > D
- **独立标记**：FULL COMBO(0 Miss)、ALL PERFECT
- **开局留白**：点开始后 5 秒倒计时，期间不落音符。实现方式是时钟从 -5 秒走、
  音频延后启动，保证谱面与音乐严格对齐
- **连击里程碑**：50/100/之后每 100 触发全屏特效，分三档升级

改判定或计分后跑：`node tests/test_hold.js`（验证长按五种松手时机）。

## 性能约束（重要）

移动端 WebView 上曾出现录屏卡顿，已优化。**修改渲染代码时不要破坏这些**：

- 每帧绘制路径里**不得**出现 `createGradient` 或 `shadowBlur`——
  两者在 iOS WebKit 上极慢。音符预渲染成离屏 sprite，渐变在 resize 时构建并缓存
- dpr 封顶 1.5
- HUD 合并到每帧一次写 DOM；进度条每 6 帧一次
- 自适应降档：帧率低于约 38fps 自动减少粒子（最低 35%），
  但音符/判定线/判定文字等**读谱必需元素不受影响**
- 音符用滑动窗口游标，不每帧遍历整首歌

## 环境坑（iSH / Alpine）

以下坑排查耗时很久，遇到直接按下面处理：

1. **ffmpeg 往管道写 raw PCM 得到空输出**（此构建 lavfi 也被禁用）。
   解法：走临时文件中转，不用 `-` 管道。
2. **numpy float32 参与混合运算或 `astype` 会段错误**。
   解法：音频解成 `s16le`，用 `int16 * (1/32768)` 直接升到 float64，**全程 float64**。
3. **`<audio>` 元素不解码 data URI / minis:// 源**。
   解法：用 Web Audio API 手动 `decodeAudioData`，并以 `AudioContext.currentTime`
   作为主时钟——音游本来就该这样，精度远高于 `<audio>.currentTime`。
4. **iOS 音频需用户手势解锁**，且 `resume()` 不能排在 `await` 之后。
   解法：`audio.unlock()` 在任何 `await` 之前调用。
5. **音频编码器**：此构建无 libopus（仅解码）。AAC 可用且低码率优于 MP3，
   故默认 AAC 64k/32kHz 单声道。

## 文件说明

开发时用多文件结构，分发时打包成单文件，两者并存不冲突。

```
节奏锻造师/
├── SKILL.md              # 本文件（给智能体读的指令）
├── LICENSE               # MIT
├── scripts/              # Python 工具链
│   ├── forge.py          # 一键流水线（推荐入口）
│   ├── beatmap.py        # 音频分析 + 谱面生成 + 可玩性约束求解
│   ├── validate.py       # 五类可玩性冲突校验
│   ├── embed_audio.py    # 音频编码并内嵌
│   └── build.py          # 打包单文件 HTML
├── template/             # 游戏本体模板（forge.py 复制到工作目录）
│   ├── index.html
│   ├── style.css
│   └── game.js
└── tests/                # 测试
    ├── test_hold.js      # 长按计分测试宿主
    └── test_hold_inner.js
```

**本 Skill 不含任何音频素材**，用户需自备音乐文件。
生成的 `audio.js` / `beatmap.js` / `song.m4a` / 单文件产出都携带版权音频，
不要提交到公开仓库。

## 反例与黑名单（修改本 Skill 时不要做的事）

| # | 不要做 | 为什么 | 替代做法 |
|---|---|---|---|
| 1 | **渲染路径里用 createGradient 或 shadowBlur** | iOS WebKit 上极慢，密集段一帧几十次调用直接卡死 | 预渲染离屏 sprite，渐变在 resize 时构建并缓存 |
| 2 | **numpy 音频处理用 float32** | 此环境 float32 混合运算/astype 会段错误 | 解成 s16le 后 int16*(1/32768) 全程 float64 |
| 3 | **ffmpeg 往管道写 raw PCM** | 此构建管道输出为空 | 走临时文件中转 |
| 4 | **用 `<audio>` 元素加载音频** | 此 WebView 不解码 data URI / minis:// 源 | Web Audio decodeAudioData + AudioContext.currentTime |
| 5 | **AudioContext.resume() 排在 await 之后** | iOS 认为脱离用户手势，不出声 | unlock() 在任何 await 之前调用 |
| 6 | **改了谱面生成逻辑不跑 validate.py** | 五类冲突可能静默出现，谱面打不了 | 每次改动后必须校验，全为 0 才算完成 |
| 7 | **把音频产物提交到仓库** | 携带版权音频，法律风险 | .gitignore 已挡住 audio.js/beatmap.js/song.*/dist/ |
| 8 | **用固定阈值分轨（如 low > 0.55）** | 低频厚的歌几乎全进中间两轨 | 用该曲自身中位数做相对划分 + 计数配平 |
| 9 | **长条尾判定用二元（全有/全无）** | 79% 和 1% 同等惩罚，太粗暴 | 三档：≥80% Perfect / ≥50% Good / <50% Miss |
| 10 | **准确率权重用 Great=0.7** | 触屏延迟下大量 Great 拖垮准确率，体感很差 | 用 0.85（参考 IIDX） |
| 11 | **判定窗口照搬 PC 端 ±45ms** | 手机触屏有 50-80ms 延迟，45ms 几乎打不到 Perfect | ±55ms（参考 Arcaea/Phigros） |
| 12 | **静默处理慢歌密度偏低** | 用户会以为分析出错 | 主动告知是歌的性质，建议提高 --hard-extra |

## 交付要求

- 产出必须真正可玩，不是"看起来完成了"。校验脚本必须全绿。
- 报告数据用表格（三档的音符数、密度、长条数、轨道分布）。
- 单文件产出移到 `/var/minis/workspace/` 下，给 Markdown 链接让用户可直接点开。
  （使用 `--out /var/minis/workspace/<歌名>-音游.html`）
- 如果做了权衡（降码率、慢歌密度偏低、裁剪副歌），主动说明原因，不要默默处理。
