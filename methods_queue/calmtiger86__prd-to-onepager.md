# PRD → One-pager

PRD를 압축된 실행 계약으로 바꾼다. 구현·검증·의사결정에 영향을 주는 사실과 1차 참조는 보존하고, 그 밖의 산문만 제거한다.

one-pager는 원본 PRD를 대체하지 않는다. 핵심 결정을 빠르게 내릴 수 있게 만들고, 상세 판단이 필요할 때는 권위 있는 원본·스키마·목업·테스트·코드로 즉시 이동하게 한다.

## 작업 원칙

- 주어진 요구사항을 증거로 취급한다. 없는 제품 정책, 역할, 예외를 발명하지 않는다.
- 추출한 문장을 내부적으로 `[Explicit]`, `[Derived]`, `[Open]`으로 구분한다.
  - `[Explicit]`: 원문에 명시된 사실. 요구사항으로 작성 가능.
  - `[Derived]`: 명시 사실에서 나온 추론. 요구사항으로 쓰지 말고 근거와 함께 열린 결정 또는 분석 메모로 다룬다.
  - `[Open]`: 결정되지 않은 사실. 구현 가정으로 바꾸지 말고 열린 결정으로 작성한다.
- 각 요구사항은 하나의 검증 가능한 의무로 작성한다: **행위자/시스템 + 조건 또는 트리거 + 관측 가능한 결과**.
- 상세 산문보다 직접 산출물을 우선한다. 스키마, API 계약, 목업, 테스트, 대시보드, 기존 코드 경로는 복제하지 말고 참조한다.
- 올바른 설계·보안·릴리스·측정을 실제로 막는 질문만 한다. 나머지 불확실성은 안전한 임시 동작과 함께 문서에 남긴다.

## 작성 절차

1. **입력 확보**
   PRD 전체와 지목된 파일을 읽는다. PDF·DOCX 등은 현재 환경에서 사용할 수 있는 추출 도구로 내용을 확인한다.

2. **사실 원장 작성**
   결과, 행위자와 권한, 범위와 비목표, 동작과 실패 경로, 제약, 의존성, 성공 증거, 미결정 사항, 1차 출처를 비공개로 추출한다.
   복합 요구는 분리한다. 예: “관리자만 승인하고 로그는 1년 보관”은 권한과 보존 요구 두 개다. 모순이 있으면 어느 한쪽을 고르지 말고 둘 다 기록한다.

3. **one-pager 작성**
   아래 구조에 `[Explicit]` 사실만 요구사항으로 옮긴다. 상세 정보는 References에서 권위 있는 출처로 연결한다.

4. **진단 및 반환**
   진단을 통과하도록 고치거나, 고칠 수 없는 항목은 열린 결정으로 드러낸다. 기본적으로 완성된 one-pager를 응답으로 반환한다. 파일 저장·공유는 사용자가 명시적으로 요청할 때만 수행한다.

## 출력 구조

원문 언어로 작성한다. 한 화면에서 핵심을 훑을 수 있을 정도로 압축하되, 길이 제한 때문에 요구·제약·결정을 누락하지 않는다.

~~~markdown
# <기능 또는 이니셔티브> — 실행 One-pager

## 성과
- **문제:** <누가 겪는 어떤 비용 또는 원치 않는 상태인가>
- **목표 변화:** <관측 가능한 최종 상태>
- **성공 신호:** <지표, 임계값, 측정 기간/출처 — 알 때만>

## 범위
- **In:** <포함할 기능, 표면, 인터페이스>
- **Out:** <명시적 비목표>

## 행위자·소유권·의존성
| 행위자/시스템 | 책임 또는 권한 | 계약 / 진실의 출처 |
|---|---|---|
| ... | ... | <링크, 경로, 스키마, API, 담당자> |

## 요구 동작
| ID | Given / 트리거 | 시스템은 반드시 | 관측 결과 / 실패 동작 | 출처 |
|---|---|---|---|---|
| R1 | ... | ... | ... | <PRD 섹션 또는 권위 참조> |

## 불변식·제약
- <권한, 안전, 데이터, 성능, 호환성, 보존, 컴플라이언스 규칙>

## 합격 증거
| 요구 또는 성과 | 핸드오프 전 증명 | 테스트 / 계측 위치 |
|---|---|---|
| R1 | ... | ... |

## 열린 결정
| 필요한 결정 | 왜 중요한가 | 소유자 / 결정 트리거 | 안전한 임시 동작 | 근거 |
|---|---|---|---|---|
| ... | ... | <모르면 미지정> | ... | <명시 사실 또는 참조> |

## 참조
- **1차 PRD:** <경로 또는 URL>
- <권위 있는 산출물 — 왜 이것이 진실의 출처인지>

## 준비도
**Ready / Ready with questions / Needs decision** — <제한 조건 한 문장>.
~~~

## 필드 규칙

- **성과:** 활동이 아니라 결과를 쓴다.
- **범위:** 기능 경계와 인터페이스를 쓴다. 명시되지 않은 인접 기능은 Out으로 둔다.
- **요구 동작:** 권한, 상태 전이, 실패 경로가 명시되었거나 구현 결과를 바꿀 때 포함한다. `R1`, `R2`처럼 안정적인 ID를 쓴다.
- **출처:** 각 요구가 어디에서 나왔는지 짧게 가리킨다.
- **불변식·제약:** 무조건 지켜야 할 규칙은 동작 행에 있더라도 별도로 보인다.
- **합격 증거:** 핵심 성과와 불변식마다 증명 또는 반증 방법을 둔다.
- **열린 결정:** `TBD`만 쓰지 않는다. 선택의 내용, 영향, 결정 주체 또는 트리거, 결정 전 안전한 기본 동작을 적는다.
- **참조:** 원본을 다시 요약하지 않는다. 구현자가 상세 판단을 해야 할 때 읽을 고충실도 자료를 연결한다.

## One-pager doctor

전달 전 아래 항목을 확인한다. 실패하면 문서를 고치거나 열린 결정으로 표면화한다. 실패를 조용히 삭제하거나 가정으로 메우지 않는다.

| 점검 | 통과 기준 | 조치 |
|---|---|---|
| 의도 | 목표 변화와 성공 증거가 보임 | 활동과 결과를 분리하고, 누락 지표는 열린 결정으로 이동 |
| 원자성 | 요구 행마다 독립적으로 검증 가능한 의무 하나 | 복합 문장을 분리하고 ID 부여 |
| 범위 | In/Out이 인접 기능 표류를 막음 | 비목표·인터페이스 경계 추가 |
| 권위 | 권한, 소유자, 진실의 출처가 명확 | 역할·시스템·권위 참조를 명시 |
| 모순 | 경쟁하는 요구를 임의로 병합하지 않음 | 양쪽 출처를 남기고 열린 결정 생성 |
| 운용성 | 필요한 실패 경로, 데이터 보존, 의존성 동작이 보임 | 요구·제약·열린 결정 보강 |
| 검증성 | 핵심 성과와 불변식에 증거가 있음 | 테스트·지표·감사·모니터링 추가 |
| 참조 적합 | 핵심 결정은 one-pager로 가능하고, 상세 판단은 권위 참조로 이동 가능 | 중복 서술을 참조로 대체하거나 누락 참조 추가 |
| 압축 안전성 | 압축 중 요구·제약·결정을 잃지 않음 | 누락 사실을 복원하거나 열린 결정으로 표면화 |
| 판단 | 명시된 위험 없이 임의 절차를 강제하지 않음 | 결과와 제약은 유지하고 불필요한 절차 지시 제거 |

`Needs decision`일 때만 one-pager 뒤에 최대 다섯 개의 차단 질문을 덧붙인다. `Ready with questions`이면 안전한 임시 동작을 적용한 one-pager만 반환한다.

방법론의 근거 또는 스킬 개정이 필요할 때만 [references/context-engineering.md](references/context-engineering.md)를 읽는다.
