# resume-forge · 简历锻造

一条流水线做三件事：**挖料写强 → 防伪门禁 → 排版交付**。

设计前提：简历写得弱，90% 是料没挖出来，不是文笔问题；简历写崩，90% 是包装超出了能守住的边界。所以这个 skill 的两个抓手是「手法库」和「门禁」，缺一个都会翻车。

**唯一红线：只放大，不虚构。** 每条写上去的内容必须能在面试里守住 15 分钟追问。守不住的包装是负资产 —— 不是零收益，是负收益。

## 何时使用

- 用户要优化 / 改写 / 从零写简历，或把口头描述的经历转成 bullet
- 用户扔来一份简历问"这写得怎么样 / 帮我改强一点"
- 用户要把简历内容导出成 PDF、要"排版好看的简历"
- 用户投递前想做一次自检（口径、热词、角色强度是否守得住）
- 用户要审计别人的简历 / 做候选人经历核验 → 走 §6 审计模式

## 流水线总览

```
S1 挖料      → 补齐 6 类缺失信息（不够就问，别急着写）
S2 排序      → 头部 5 行压进最稀缺信号
S3 改写      → 手法层 + 句式层双清单逐条套用
S4 门禁 ★   → 确定性校验（脚本）+ 答辩模拟（对话）—— 不可跳过
S5 排版      → 填模板 → 渲染 → 压页 → 视觉验收
```

★ S4 是这个 skill 与普通"帮我改简历"的根本区别。**S3 产出的稿子在通过 S4 之前不算成稿，不得进入 S5，也不得作为最终答复交付给用户。**

## S1 · 挖料（先问，别急着写）

用户给的初始素材几乎总是不够。对每段经历追问这 6 类，缺哪类补哪类：

| 类别 | 追问 | 为什么要 |
|---|---|---|
| **角色强度** | owner / 核心成员 / 参与者？从 0 到 1 还是接手维护？ | 决定能不能用 ownership 语言，见 §角色强度分级 |
| **数字** | 任何维度：性能、成本、耗时、调用量、用户量、转化率、覆盖率、star、名次 | 说"没有数字"时帮他推算：上线前后对比？人工 vs 自动化耗时？服务多少人/多少次调用？ |
| **旧方案** | 原来什么样，为什么不行，你改成了什么 | 这是判断力叙事的原料，比"做了什么"值钱得多 |
| **外部锚点** | GitHub 链接、线上域名、开源身份、比赛名次、内部榜单/等级 | 少数几个真实可查的锚点会让其余内容集体沾光 |
| **极值** | 最年轻的、第一个、排名第一的、唯一的 | 哪怕限定词很多（"公司内该方向排名第一"）也有效 |
| **反差** | 跨界背景、非典型起点、小众爱好里做出的东西 | 给面试官一个转述你时的记忆句柄 |

若用户丢来现成简历：先用 @references/exemplar.md 的 11 个手法当检查表做**逐条诊断**，标出每条缺什么，再针对性挖料。

若用户只给了口头描述：**先输出挖料问题清单，拿到回答再写。**不要凭空补。

## S2 · 信号排序（头部即胜负）

面试官平均 30 秒扫一份简历，前 5 行决定他用什么心态读剩下的。

- 把最稀缺、最可验证的 2–4 个信号压进姓名下方的简介行
- 经历排序按**信号强度**，不必严格按时间。最硬的一段放最前
- 每个头部信号配可点击 / 可搜索的锚点
- 弱经历一行带过或直接删。**敢删和敢写同样重要** —— 弱条目会稀释强条目的密度

## S3 · 逐段改写

统一叙事骨架，读起来像 mini 技术方案而不是岗位描述：

```
项目名 | 一句话定位（借势：绑到大公司/大项目/热方向）
背景与目标：旧方案的痛点是什么 → 要解决什么
我的职责：ownership 定位（owner / 核心作者 / 主导 X 到 Y 的升级）+ 具象锚点
技术链路：具体到架构决策和参数级细节
指标：量化收益，用「约 / + / 区间」留余地
```

**改写时必须打开两份参考，双层对照：**

- @references/exemplar.md — **手法层（做什么）**，11 个手法附片段示例，当检查表逐条过
- @references/phrasebook.md — **句式层（怎么写）**，13 个句式模板，每条给「片段 → 抽象模板 → 适用条件与风险」

高频的几条，展开在这里以免漏用：

1. **Ownership 语言** — 能说"主导 / owner / 从 0 到 1"就不说"参与 / 协助"。**但必须与 S1 确认的真实角色一致**，见下方分级表。
2. **演进叙事** — 写"1.0 有什么病症 → 我改成 2.0 → 可感知收益"，而不是平铺功能列表。收益敢写"零改动""只动对应层"这种绝对化但可验证的表述，比"大幅提升可维护性"强一个数量级。
3. **热词命名** — 把做的事映射到行业当前热词（上下文裁剪 → Context Engineering；打分脚本 → LLM-as-Judge）。**前提：用户能讲清这个术语，否则是自爆按钮**，S4 会强制过一遍。
4. **细节密度** — 写到参数级（并发数、超时阈值、token 阈值、压缩策略）。具体数字＝可信度，密度本身就是威慑。
5. **量化留余地** — `+25%+`、`约 30%`、`月均 600+ 次`。区间和约数比精确数字更可信也更难被证伪。
6. **每个宏大陈述配一个微观锚点** — 说"完全负责系统架构"就附一条 CLI 命令；说"开源核心作者"就附 GitHub 链接。宏观负责叙事，微观负责可信。
7. **绝对化收益 + 模糊化数字** — 定性收益敢写死，定量数字留缓冲。反过来（定性含糊 + 数字精确到小数点）是业余信号。

### 角色强度分级（硬约束）

改写时角色词必须按用户提供的原始表述映射，**不得越级**：

| 用户原话 | 可以写成 | 不可以写成 |
|---|---|---|
| 独立负责 / 我一个人做的 | `模块级 Owner`、`端到端链路 Owner`、`从 0→1`（**必须限定到具体模块**） | 整个平台/项目的 Owner |
| 主要负责 / 我主导的 | `策略架构 Owner`、`方向负责人`、`主导 X→Y 演进` | 唯一作者、独立完成 |
| 参与 / 共建 / 配合 | `系统级共建者`、`核心参与者` | Owner、主导、核心作者 |
| 计划 / 在做 / 探索中 | `当前方向`、`规划中`（保持规划时态） | 任何已完成/已上线的收益表述 |

每个重点项目先做一次 **Owner 化拆分**：找出用户真正独立或主要负责的**最小闭环**（如"数据治理链路""策略架构""量化部署"），对这个闭环用 Owner / 0→1，但**不把词的作用域外扩到整个项目或公司平台**。

只是优化存量系统时，不要写 `0→1`，改写为 `X→Y 架构演进`。

### 输出格式

- 简历正文用 markdown，保持用户原有语言（中文简历就中文，术语可保留英文）
- 每段改写后附一句**改动说明**：用了哪些手法、哪些数字需要用户确认口径
- 信息缺口一律写成 `待确认：xxx`，S5 排版时会渲染成黄色高亮，视觉上无处可藏

## S4 · 防伪门禁（不可跳过）

两道闸门，一道靠代码，一道靠对话。**两道都过才算成稿。**

### 闸门 A：确定性校验（脚本，不靠模型自觉）

模型最容易在数字上翻车 —— 不是恶意造假，是算错。把可疑数字整理成 JSON 交给脚本重算：

```bash
python3 scripts/audit.py --claims /absolute/path/claims.json
```

`claims.json` 格式（只填**材料里明确给出**分子分母/基线结果的项，不要从"转化率 38%"这种自然语言猜分母）：

```json
{
  "claims": [
    {
      "id": "C-001",
      "text": "付费转化率约 38%",
      "role_source": "独立负责",
      "role_written": "模块级 Owner",
      "metric": { "numerator": 200, "denominator": 2000, "displayed_percent": 38 }
    },
    {
      "id": "C-002",
      "text": "通过率较全量重跑提升约 25%+",
      "metric": { "baseline": 100, "result": 125, "change_type": "relative_percent", "displayed_change": 25 }
    }
  ]
}
```

脚本会做四件模型做不可靠的事：

1. **比例重算** — `numerator/denominator` 对不上 `displayed_percent` 直接报错（200/2000 = 10%，不是 38%）
2. **变化类型区分** — `relative_percent` 按 `(result-baseline)/baseline*100`；`percentage_points` 直接相减。**60%→70% 是 10 个百分点，不是 10% 的相对变化**（相对变化约 16.67%）。这是最高频的口径错误
3. **角色越级检测** — 比对 `role_source` 与 `role_written`，参与类写成 Owner 类直接报错
4. **规划时态检测** — 标了 `"planned": true` 的条目若含已完成强角色词或已上线收益，报错

数字关系不一致**不等于**用户造假 —— 可能存在未披露的更窄分母。报错时的正确动作是**回去问用户口径**，而不是直接删掉或改数字。

成稿 HTML 出来后再扫一遍：

```bash
python3 scripts/audit.py --html /absolute/path/resume.html
```

检查：`待确认` / `todo` 残留、模板占位符未替换、外部资源引用、极值词是否缺限定范围。

### 闸门 B：答辩模拟（对话，不靠脚本）

逐条过成稿，对每个 claim 问四个问题：

1. **追问 3 层能守住吗？** —— "这个 25% 怎么测的？baseline 是什么？为什么不是 20%？" 守不住 → 降级措辞或删掉
2. **数字口径能一句话说清吗？** —— 每个数字用户要能张口就答来源
3. **热词能定义吗？** —— **让用户口头解释一遍简历里的每个术语**，卡壳的换成平实说法。这一步不能省，热词是面试官的必问点
4. **ownership 会被背调 / 交叉面试戳穿吗？** —— 团队项目里把队友的活写成自己的，是最常见的死法

**把降级 / 删除的条目告诉用户并说明原因。**这本身就是给用户的面试预演，价值不低于改写。

## S5 · 排版交付

只管视觉，不碰文案。视觉规格是从一份真实爆款简历逐 span 逆向的精确参数。

1. **填模板** — 复制 @assets/template.html 到工作目录，把 `{{内容}}` 替换为按模板注释里的组件写的正文。组件清单和用法都在模板注释块里（**用完删掉注释**）。
   **不要改 CSS** —— 所有色值、字号、边距都是逆向出来的规格，改了就不像了。

2. **渲染** — 跨平台，自动探测 Chrome：
   ```bash
   python3 scripts/render.py <input.html> <output.pdf>
   ```
   脚本会报告页数。

3. **压页** — 目标是**排满**，不是塞满也不是留白。超出时按顺序试：
   1. 删内容（弱条目一行带过或删除）
   2. 微调 `.page` 的 padding 和 `li` 的 margin-bottom（±1–2px 级别）
   3. 行高 1.6 降到 1.5（下限）
   
   **不到万不得已不缩字号。**校招 / 3 年以内经验目标一页；资深候选人两页也成立，但每页都要排满。

4. **视觉验收** — 用 PyMuPDF 把第一页渲成 PNG 自查（`pip3 install pymupdf`）：
   ```python
   page.get_pixmap(matrix=fitz.Matrix(2,2))
   ```
   确认：中西文混排正确（西文应是衬线）、分节线全宽、灰带行日期右对齐、无孤行溢出、无黄色 `待确认` 残留。
   
   PyMuPDF 装不上时降级：用 `scripts/audit.py --html` 扫一遍 + 人工看 PDF，但要告知用户跳过了像素级验收。

5. 把 PDF 交给用户（`present_files`）。

### 排版原则

- **加粗只给数字、热词、极值词** —— 扫读时眼睛只落在信号上。整句加粗是错的
- **密而不乱** —— 这个风格靠高信息密度 + 清晰层级立住，留白多了反而露怯
- 图标用 emoji（📞 ✉️ 💬 👤 🐙 🎓），宽度由 `.ico` 统一
- 链接真实可点（`<a href>`），可验证锚点是这个风格的信用基础

## §6 · 审计模式（审别人的简历）

用户要核验他人简历 / 做候选人经历尽调时，切到这条支线。核心方法：**把简历当成一组可独立检验的主张，而不是判断一个人好或坏。**

### 拆原子主张

不要整段判断。把角色、范围、结果、因果**分开**检验。例：

> "作为核心作者主导项目从 1.0 到 2.0，性能提升 25%"

拆成 4 条：① 是否为核心作者 ② 是否领导了 1.0→2.0 ③ 25% 是否成立 ④ 该提升是否可归因于本人。

### 五档证据状态（每条主张只用一个）

定状态前先读 @references/evidence-methodology.md —— 里面有 A/B/C/D 四级来源层级表（什么来源能证明什么）、各状态的判定规则、置信度分级和反证检查清单。

| 状态 | 含义 |
|---|---|
| `corroborated` | 强独立证据支持主张的关键内容 |
| `partially_corroborated` | 真实事实存在，但角色 / 范围 / 因果 / 幅度超出证据 |
| `contradicted` | **可靠证据与主张直接冲突**（门槛最高，慎用） |
| `unsupported` | 合理搜索后仍无足够证据 |
| `unverifiable` | 只有当前不可取得的内部 / 私人记录才能核验 |

同时记录置信度（high / medium / low），并写明**什么证据可以改变结论**。

### 检查顺序（先便宜的，后贵的）

1. **内部一致性**（不用联网，最高置信度）—— 重算所有比例和增长率；比对日期是否重叠；找无比较范围的极值词；区分项目整体指标与个人影响指标；检查无 baseline 的因果宣称。用 `scripts/audit.py --claims` 跑
2. **一手来源** —— 开源主张查 PR 状态（merged / closed-unmerged 区别很大）、改动文件、CODEOWNERS、release note、贡献时间与所称版本阶段的关系，清单见 @references/open-source-audit.md；学历主张分开核验录取院校 / 就读校区 / 合作院校 / 学位授予方，见 @references/education-branding-audit.md；指标主张要求定义分母和时间窗口
3. **夸大模式** —— 见 @references/inflation-patterns.md。**必须先完成逐条核验再判断模式**，模式只是调查信号，不能单独作为造假证据

### 伦理边界（硬约束，不可让步）

- 只用**公开且与任务直接相关**的信息。不搜集住址、电话、家庭成员、私人消息、无关个人信息
- 截图、指控文章、匿名评论、当事人自有主页只能证明"有人这样说过"，不自动成为独立证据
- 用精确表述（"公开证据仅支持 contributor，尚未支持 core author"），**不用人格标签**（骗子、欺诈者）
- **不得用学校排名 / "双非"身份推断诚信。**要核验的是院校、项目、学籍、学位授予方
- 性别、外貌、性格、动机推断与简历真实性无关，排除
- **对当事人有利的证据必须与不利证据同等展示**
- 指控必须带归属：写"文章作者指控……，当前材料缺少原始截图，尚未独立验证"，**不写**"当事人伪造了……"
- **不要把针对特定在世个人的负面核验结论写入可长期分发的文件**（skill 参考文档、公开仓库）。审计产出是一次性交付物，给用户，不留档

### 交付顺序

最强的已证实事实 → 最强的直接矛盾 → 最大的不可核验缺口。明确区分「字面虚构」/「角色范围膨胀」/「缺乏支持的营销表述」/「仅仅缺少证据」—— 这四件事的严重程度完全不同。

### 报告交付（可选，需要留档时）

对话里给结论适合快速自检；**要把审计结论交付给第三方（招聘方、背调协作方）时，产出正式报告**：

1. 按 @references/report-schema.md 整理 `report-data.json`（主张 + 来源 + 五档状态 + 模式 + 时间线），样例见 @references/examples/report-data.example.json
2. 渲染 + 校验：

```bash
python3 scripts/render_report.py --input report-data.json --html report.html --pdf report.pdf
python3 scripts/validate_report.py --data report-data.json --html report.html --pdf report.pdf
```

HTML 是自包含单文件（JSON 注入 + 客户端渲染），PDF 复用 `scripts/render.py` 的 Chrome 渲染链路，不需要 reportlab。

3. 审计自己的简历（S4 门禁的延伸）时同样可以用这条链路：把 S4 闸门 B 答辩模拟中没守住的条目整理成 claims，状态标 `unsupported` 或 `partially_corroborated`，生成一份「投递前自审报告」留档。

**报告是一次性交付物**：交给用户后不在 skill 目录、公开仓库里留档，尤其涉及特定在世个人的负面结论。

## 边界

- **不虚构**经历、数字、头衔、身份。用户要求编造时明确拒绝，并解释：被戳穿的负收益远大于平淡的负收益
- 极值标签必须真实成立 —— 可以加限定词收窄范围让它成立，不能凭空造
- 手法为技术岗（AI / 算法 / 工程）调校。非技术岗可复用骨架和句式，但"热词命名"一节要换成对应行业热词
- 模板只有一种视觉风格。用户明确要另一种风格（如外企 ATS 友好的纯文本版）时，如实说明并改用朴素排版，不要硬套

## 常见坑

- **跳过 S4 直接交付** —— 这是最严重的失败模式。S3 的稿子看起来很漂亮，正因为漂亮才需要门禁
- **热词没让用户口头过一遍** —— 简历里每个术语都是面试官的必问点
- **把 `percentage_points` 当 `relative_percent`** —— 60%→70% 写成"提升 10%"是错的，那是 10 个百分点 / 约 16.67% 相对提升
- **角色词悄悄越级** —— "参与"改写成"主导"是最容易被背调戳穿的死法
- **改了模板 CSS** —— 视觉规格是逆向出来的整体，动一个色值或字号就失去原版气质
- **`待确认` 残留进终稿** —— 黄色高亮是给用户看的中间态，交付前必须清零
- **审计模式里把"缺少证据"等同于"造假"** —— 这两件事差别极大，混淆会造成真实的名誉伤害
- **PDF 没做视觉验收就交付** —— 中文缺字、孤行溢出、日期没右对齐，肉眼一眼可见，脚本查不出来

## 验证

交付前必须全部为是：

- [ ] S1 的 6 类信息都问过（或明确记录了用户答不出的项）
- [ ] 每条 bullet 的角色词与用户原始表述匹配，未越级
- [ ] `scripts/audit.py --claims` 通过，或不一致项已回问用户口径
- [ ] 每个热词用户能口头定义（已当面过一遍）
- [ ] 每个数字用户能一句话说清口径
- [ ] `scripts/audit.py --html` 通过（无 `待确认` 残留、无占位符、无外链）
- [ ] PDF 页数符合预期且每页排满
- [ ] 第一页 PNG 视觉验收通过（或已告知用户跳过）
- [ ] 已把 S4 中降级 / 删除的条目和原因告诉用户

## 环境说明

首次使用建议先跑一次自检，确认渲染链路可用：

```bash
bash scripts/selftest.sh
```

渲染有两条路径，脚本自动选择：

1. **Playwright 驱动系统 Chrome**（优先）—— 在带沙箱的运行时里唯一稳定的路径，也是 `--measure` 溢出测量的必要条件
2. **Chrome CLI `--print-to-pdf`**（兜底）—— 零依赖，但在某些受限环境会被 SIGKILL（exit 137）

环境变量可覆盖探测结果：`CHROME_PATH` 指定浏览器，`NODE_PATH` 指向含 playwright 的 `node_modules`。

压页时用 `--measure` 先量后调，别盲改 CSS 反复重打：

```bash
python3 scripts/render.py resume.html resume.pdf --measure
```

它会报告 body 相对 A4 单页（≈1122px）的溢出量。换算参考：`line-height` 每降 0.01 ≈ 60 行省 7px；padding 1mm ≈ 3.8px。
