# 品味 · 产品定义

> 这份文档回答四个问题：解决谁的什么痛点、为什么是我们、产品怎么表达、人为什么会再来。
> 写于 2026-08-19 立项。所有判断都可以被推翻，但要给出理由。

---

## 一、痛点：不是"找不到"，是"不敢装"

Agent Skill 的生态到底有多大，**没有人能从外部核到底，我们也不行**。

能说的只有三句，每句都标了出处和口径：

1. **GitHub 上叫 `SKILL.md` 的文件是百万量级** —— GitHub 自己的代码搜索索引报约 **562 万个**
   （`gh api '/search/code?q=filename%3ASKILL.md' --jq '.total_count'`，2026-08-20 实测）。
   **这个数本身也是估算**：同一接口三次取样全是 1024 的整数倍
   （SKILL.md 5,619,712 = 5488×1024 · AGENTS.md 768,000 = 750×1024 · README.md 60,030,976 = 58,624×1024），
   GitHub 在这个量级做了分桶。所以只能说「百万量级」，**不许印 5,619,712**。口径是**文件**不是仓库。
2. **最大的目录站自报收录 266 万** —— 那是 SkillsMP 首页原文「2,664,116 Collected SKILL.md files」。
   而**它的 sitemap 只放得出 1.3 万个 skill 页 = 自报数的 0.50%**。
3. **三家目录站的自报数差三个数量级**（266 万 / 2.36 万 / 1.5 万），
   而三家能对外枚举的量又都远小于各自的自报数。

所以「生态一共多少件」这一栏**写「未知」**。

> **这一句原先写的是「生态已有 266 万条」，错了两层**：把 SkillsMP 的数记成了 skills.sh 的，
> 而且拿一家目录站的自报库存当了世界。**改的不是数字，是分母。**

检索早就不是瓶颈了。

用户真正卡住的地方不是"有没有"，是这三句心里话：

1. **"我装了会不会白花半小时"** —— 装一个 skill 的成本不是磁盘，是注意力和信任。踩一次坑，下次就不装了。
2. **"这玩意儿跟我上周装的那个有什么区别"** —— 同类第 N 个 code review、第 N 个 planning，用户分不出来，也没义务分。
3. **"我想找的那种东西，搜不出来"** —— 尤其是中文用户。

目录站解决第一层（有没有），**没有任何人解决第二层（值不值）**。
skills.sh、SkillsMP 这类以收录量为模式的站，结构上不可能解决——它们的 KPI 是收得多，判断是负担。

**所以品味的产品定义只有一句：我们卖判断，不卖索引。**

## 二、为什么是我们：空白在长尾，不在语言

**这一节被我们自己的数据改写过一次，改写的过程比结论更值得留着。**

### 原来的说法，以及它错在哪

原文写的是「所有大市场都是英文爬虫、英文搜索，**中文创作者的东西在那边基本不存在**」。

**事实部分是对的**——中文的东西确实不在那边。**但归因是错的。**

内容做了一组对照实验：30 条同概念的英文垂直词（tarot / astrology / feng shui /
acupuncture / resume / civil service exam / tax filing / recipe / fishing /
birdwatching / knitting / woodworking / calligraphy / beekeeping / retirement planning …），
走同一条漏斗、量同一个指标：

| 词表 | GitHub 搜到的仓库 | 其中被 skills.sh 收录 |
|---|---|---|
| **英文垂直对照组** | 1256 | 6 = **0.48%** |
| **中文垂直词表** | 3250 | 16 = **0.49%** |

**0.48% 对 0.49%。没有差距，一点都没有。**

所以站得住的结论只有一条：**大市场漏掉的是 GitHub 长尾的 99.5%，跟语言无关。**
不是「英文爬虫爬不到中文」，是**没有人在爬长尾**——英文长尾同样没人爬。

连带作废的还有更早那个「扫 6000 条、164 件里 159 件是中文」：
**那一轮的词表本来就全是中文词，捞到中文是必然的。** 那是循环论证，不是发现。

### 所以护城河是什么

**不是「中文覆盖」。** 英文爬虫哪天想补就能补，而且他们爬中文长尾和爬英文长尾的成本是一样的。

是这两件事叠起来：

1. **有人肯下到长尾里**——任何人都能抄，只是没人愿意
2. **并且肯为每一件写判断**——这一半才是真正独有的

第二条正好是第一节那句「**我们卖判断，不卖索引**」。第一条只是把货找出来，
第二条才是把货变成商品。抄走第一条的人，还是得自己面对第二条。

### 中文垂直的位置，因此要重新摆

它从**差异化本身**降级成**差异化的一个样本**。
它当初有效，是因为**没人挑**，不是因为它是中文。

这也是为什么转向全球 C 端跟这组数据是一致的、不是冲突的：
长尾里既有周易占卜和党政公文，也有 beekeeping 和 birdwatching，
**判断的稀缺性在两边一样成立**。

我们仍然会大量收中文的东西——因为我们读得懂、判得准、写得出。
但那是**能力优势**，不是**结构性壁垒**，两者不能混为一谈。

### 补一条实测（2026-08-20）：长尾里有货，但 C 端的货主要在中文侧

扩源之后必须补一句，**因为它改的是「接下来去哪儿找货」**。

skills.sh 的 `sitemap-owners.xml` 里有 9,197 个 owner/repo 页，其中 **6,669 个我们从没碰过**
（之前只读了 `sitemap-skills-1/2.xml` —— **旧源读了一半**，不是缺新源）。
补完元数据、筛出 A/B 两档 2,722 条之后，**2,722 条逐行读完**（不抽样），
按「为自己装还是为工作装」这把尺子，可能是 C 端的 **193 条（7.1%）**，
最后**留下 24 件 —— 池子里的通过率 12%**。

> 我第一版用正则粗筛得 83 条（4.9%），并注明「正则偏松、真实更低」。**两个数字都错了，
> 而且错的方向相反。** 漏掉的不是词，是整批**从头到尾不会说 life / family / health 的形状**：
> 以色列餐厅订位 · 法国官僚流程 · Apple 语音备忘录 · C 盘清理 · 闲鱼蹲货 · 占星。
> 同时又把 `rust-skills` 这种框架仓库多算了进来。
> **说「这个数偏松」的时候，我已经在心里认定误差是单向的了。**（D67）

真实的形状是：**C 端池子比预想的大，但池子里能过尺子的极少。** 这批压倒性地是开发 / agent 工具。

同一天另一次独立测量对上了：选货同事报「英文侧几乎是空的 ——
用 pet / baby / parenting / eldercare 等 40 个英文词扫全池，只捞回 10 条，
全是虚拟宠物引擎和桌宠 Electron」。

**这一条跟上面那一节说的不是同一件事，不要混：**

| | 说的是 | 结论 |
|---|---|---|
| 上面（对照组） | **覆盖** | 目录站对英文垂类和中文垂类收录率一样低（0.48% / 0.49%）→ 空白在长尾，不在语言 |
| 这一条（扩源） | **存在** | C 端的 skill 在英文侧目前本来就很少 |

合起来：**长尾里有货，但 C 端的货主要在中文侧。**

这不推翻「做全球 C 端」——它推翻的是「扩源就能批量拿到英文 C 端货」这个隐含预期。
短期内英文 C 端**供给还没长出来**，我们是早到的，不是找错了地方。
所以进货策略是：**中文长尾照旧下深，英文侧不指望批量、按件捞**，
并且**不许为了让英文侧的数字好看而放宽尺子** —— 那会同时毁掉尺子和数字。


### 一条方法上的教训（比结论更该留下）

内容的原话：

> 这个对照组是我自己给自己设的。**没有它，我会把一个 260 倍的差距发给你**——
> 那个数是拿 sitemap 来源的仓库当「非中文对照组」算出来的，
> 而它们 100% 在 skills.sh 里是构造出来的。

**一个太完美地印证了我们既有信念的数字，本身就该当成警报。**

## 二·五、「全球 C 端」这把尺子，先校准再用

店主的原话是「**我还是希望做 c 端用户，而且是国际化的全球用户的产品**」，
后来补了一句「**垂类可以中外混，部分中外的**」。

这把尺子正在被用来判货，所以它自己得先说清楚，否则会误伤。

### 它不是「非程序员」

装 Agent Skill 的人今天几乎都在跑 Claude Code 一类的东西，本身就偏技术。
**按「是不是程序员」筛，会把整个货架筛没。**

### 它是「为自己装，还是为工作装」

| | |
|---|---|
| **C 端** | 为自己的生活、兴趣、家人装。装完是你自己受益 |
| **非 C 端** | 为职业身份装，装完是你老板/客户/机构受益 |

按这把尺子：
- 「替猫拦下云南白药」「查花粉」「赶海」「跑团」「起名」——**C 端**
- 「按 GB/T 9704 写党政公文」「德国鉴定式民法案例」「法律中文润色」——**非 C 端**（已下架）
- 「给你装的技能库做体检」「让你写的 skill 自己迭代」——**C 端**：
  它服务的是你自己的工具，像给自己的手机装东西，不是给客户交付

### 「国际化」不等于「删掉中文内容」

D32 已经证明：**空白在长尾，不在语言**。所以中文内容不是要清掉的负担，
是长尾的一个样本。真正要做到的是**英文版能独立成立**——已完成（171 件四个英文字段全覆盖）。

### 这把尺子怎么用

**它管「接下来去哪儿找货」，不管「已经在架的要不要清」。**

一件个体质量过硬、只是偏职业的东西，**不因为分类被下架**；
但下一轮的漏斗重心应该压在「为自己装」的垂类上。

**理由**：分类是我们自己贴的标签，而三问是对着商品本身问的。
**用标签去执行标准，等于用二手信号做判断**——这正是 D40 我栽过的那一跤。

## 三、产品怎么表达

### 核心形态判断：不是货架，是专栏

**单位不是卡片，是判断。**

现在的网站是 154 件平铺的信息流，每张卡长得一模一样。人扫到第 10 张就停了——
因为没有节奏，没有主角，没有"下一个"的欲望。

有品味的东西一定有节奏：有大有小、有长有短、有主角有配角。
参照物应该是**好的独立杂志和买手店专栏**，不是 SaaS 落地页。

### 四条设计硬判断

**1. 杀掉星数。**
我们自己的标准明写着"星数是滞后且有偏的指标，会亏待新发布、垂直、非英语、无营销的好项目"，
然后又把 `★ 0` 印在每张卡的首屏上——这是自我否定。星数可以留在详情里当参考，不能当门面。

**2. 杀掉重复封面。**
上架 154 件里 **125 件没有真封面（81%）**，显示的是"把标题又写一遍"的渐变色块。
一个讲品味的站，八成图位是占位符，这件事本身就说明标准没落到实处。

两条路，都比现在强：
- **放真东西**——skill 的**产出物**截图（海报、像素图、公文、图表）。那才是品味的证据，比任何文案都有说服力。
- **彻底不放图**——纯用排版做区分。**品味是删出来的，不是加出来的。**

最差的选择是留着假图。

**3. 每条点评必须有"但是"。**
现在的点评只夸不贬。但用户的痛点是"不敢装"，
**诚实的局限比夸奖更能建立信任**——你告诉我它哪儿不行，我才信你说它哪儿行。

固定格式：`它妙在哪` + `但是（机制短板 / 平台限制 / 适用边界）`。

**4. 建立层级。**
头条 1 件（大幅 + 三百字的长判断）+ 精选 6 件 + 名录若干。
154 件全部平铺 = 没有推荐。有主角才有节奏。

### 新增内容位：拒收榜

公开"**今天扫了 6000 条，收了 3 件，拒了这些，每条一句为什么**"。

这是这个产品里我最想推的东西，四个理由：

1. 它把 `docs/CURATION.md` 的标准变成了内容，**零额外生产成本**
2. 拒收比推荐更好看、更有信息量、更有传播性——人爱看毒舌，但毒舌必须公允
3. 说"我们只收 3%"和**展示被拒的那 97%**，是完全两回事。这是筛子为真的**唯一证据**
4. 竞品结构上做不了——公开拒收与"收录量即价值"的模式直接冲突

配套：**标准的版本记录也要公开。** `editorial/feedback.json` 已经在跑一个机制——
同一类问题出现第二次，就改标准而不是只改那一件。把这个改动史摊开，
人看得见筛子在变严，才会信这不是随口挑的。

## 四、人为什么会再来（留存）

**先承认一个残酷事实：精选列表天然是一次性的。** 看一眼、收藏三个、再也不来。
这是这类产品最常见的死法，不解决它，前面三节都白写。

### 认清楚：不该指望人主动回访网站

转录里已经踩过这个坑——自制的 `find-reusable` 死在"**想不起来用**"这个死穴上。
一个要人主动记得去访问的东西，几乎必死。

所以留存要靠两条腿，**分工明确、KPI 不同**：

| | 给谁用 | 干什么 | 怎么衡量 |
|---|---|---|---|
| **网站** | 人 | 橱窗。建立信任和品牌，让人读到判断、认同这个店的口味 | 看过的人信不信（读完率、拒收榜的分享） |
| **skill 入口** | agent | 被反复调用。用户干活时**自动触发**，不需要他想起来 | 被调用多少次 |

**skill 入口是留存的真正答案**——因为它绕开了"想不起来"这个死穴。
你在写 PPT 的时候，agent 自己去查"品味里有没有做这个的"，这才是可持续的复用。

网站负责让人第一次相信我们，skill 负责让这份信任被反复兑现。

### 网站这一侧，三个机制

1. **节奏**——每次来都有新头条。不硬承诺"每日"，承诺了做不到反而伤信任。
2. **积累**——标准在变严，而且这件事看得见（公开的标准改动史）。
3. **身份**——店主要有脾气、敢说"这个我不收"。买手店的复购从来不是靠货全，是靠认同口味。

## 五、我知道的风险

不写出来就是骗自己。

1. **平台自带能力。** Claude 已经有记忆和历史检索，我们可能在做平台白送的东西。
   差别在于我们给的是**结构化的判断**（妙在哪 / 但是），不是被动回忆。这个差别够不够，没把握。
2. **人工判断不可规模化。** 机器只能筛掉明显没品味的，**挑不出有品味的**——那 11 件是人一条条读描述挑的。
   这既是护城河也是天花板：判断层没法自动化，规模上不去。
3. **一旦要人手动整理就会死。** 所以捕获必须自动、判断才是人工。这条边界不能模糊。
4. **竞品做判断。** 见第二节。这是最大的单一风险，且我们控制不了。
5. **署名与许可证欠账。** 已存 126 份方法正文，无一带原作者署名和许可证声明——
   对 MIT 项目这违反许可条件。现阶段刻意搁置（需求未验证前不做合规装修），
   但**上线放量前必须补**，否则是明知故犯。

## 六、当前状态与分工（2026-08-19）

**数据**：仓库 712 个 skill json，上架 154 件，8 个分类，126 份方法正文存档。
**已知缺口**：81% 无真封面；154 件全部缺"局限"字段；无头条位；无拒收数据。

| 负责人 | 在做 |
|---|---|
| 内容抓取 | 描述三层兜底（frontmatter → GitHub API → README）、封面补全、宽漏斗按垂直捞货、产出拒收样本数据集 |
| 用户体验 | 首页重新设计（层级/节奏/杀星数/封面降级方案/拒收榜版式），产出 `design/` 原型 |
| 功能开发 | schema 加 `limit_zh`、头条位、拒收榜数据管线、SEO 品牌不一致修复 |
| 产品（本文档） | 定方向、定标准、验收 |
